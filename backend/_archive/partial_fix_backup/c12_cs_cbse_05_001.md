## DEFINITION
SQL (Structured Query Language) is a standardized programming language used to manage and manipulate relational databases; MySQL is an open-source relational database management system (RDBMS) that implements SQL as its query language, allowing users to create, read, update, and delete data stored in structured tables.

## WALKTHROUGH
Imagine you are building a contact list for your school’s annual fest: you need to store each participant’s name, class, phone number, and event category. If you write this in a notebook, searching for “all Class 12 students in ‘Dance’” means flipping pages manually. A database solves this by organising data in tables and letting you ask questions in a language the computer understands — SQL. We start by installing MySQL (the engine) and then learn to speak to it using SQL commands. The first step is always to create a container (database) and then a structured sheet (table) with columns that have specific data types. Once the table exists, we insert rows. This node walks through that exact sequence with a concrete Indian-school example so you can run the commands yourself and see the data appear.

## DIAGNOSTIC_QUESTION_1
What is the fundamental difference between SQL and MySQL?

## DIAGNOSTIC_ANSWER_1
SQL is a language standard (ANSI/ISO) for querying relational databases; MySQL is a specific RDBMS product that implements that language. A wrong answer such as “SQL is the software and MySQL is the language” reveals the student has confused the specification with the implementation — a classic Category Error that leads to writing “MySQL queries” when they mean “SQL queries” and causes confusion when switching to PostgreSQL or SQLite later.

## DIAGNOSTIC_QUESTION_2
Explain in your own words why a column in a relational table must be assigned a data type (e.g., INT, VARCHAR(50), DATE) at creation time.

## DIAGNOSTIC_ANSWER_2
Data types enforce domain integrity: they restrict what values can be stored (e.g., preventing letters in an age column), allocate appropriate storage, and enable type-specific operations (date arithmetic on DATE, string functions on VARCHAR). A student who says “it’s just a label” misses the validation and optimization purpose; this misconception leads to schema designs that allow garbage data and slow queries.

## DIAGNOSTIC_QUESTION_3
Write the exact sequence of SQL commands to create a database named `school_fest`, switch to it, create a table `participants` with columns `pid` (integer), `name` (variable string up to 30 characters), `class` (integer), `phone` (fixed string of 10 digits), and `event` (variable string up to 20 characters), and then insert one row for a student named ‘Aarav’ in class 12 with phone ‘9876543210’ participating in ‘Dance’.

## DIAGNOSTIC_ANSWER_3
```sql
CREATE DATABASE school_fest;
USE school_fest;
CREATE TABLE participants (
    pid INT,
    name VARCHAR(30),
    class INT,
    phone CHAR(10),
    event VARCHAR(20)
);
INSERT INTO participants VALUES (1, 'Aarav', 12, '9876543210', 'Dance');
```
Missing the `USE` statement or forgetting the semicolon terminator are common syntax errors; a student who omits `USE` will create the table in the wrong database (or get an error if no database is selected). This tests the procedural understanding of database context.

## DIAGNOSTIC_QUESTION_4
Compare and contrast the storage implications and use-cases of `CHAR(10)` versus `VARCHAR(10)` for a column that stores Indian mobile numbers (always exactly 10 digits). Which would you choose and why?

## DIAGNOSTIC_ANSWER_4
`CHAR(10)` always stores exactly 10 characters, padding with spaces if the input is shorter — wasteful for fixed-length data like mobile numbers where every entry is exactly 10 digits. `VARCHAR(10)` stores only the actual characters plus a 1-2 byte length prefix, saving space when lengths vary. For mobile numbers, `CHAR(10)` is actually preferable because the length never varies, eliminating the overhead of the length prefix and guaranteeing fixed-width rows which can speed up scans. A student who picks `VARCHAR` “to save space” shows they don’t understand the fixed-length nature of the data and the trade-off between length-prefix overhead and fixed-width performance.

## DIAGNOSTIC_QUESTION_5
A classmate argues: “Since SQL is a standard, any SQL code I write in MySQL will run unchanged on PostgreSQL, Oracle, or SQL Server.” Evaluate this claim and justify your position with two concrete examples of MySQL-specific syntax or behaviour that are not portable.

## DIAGNOSTIC_ANSWER_5
The claim is false. While core DML (SELECT, INSERT, UPDATE, DELETE) and basic DDL (CREATE TABLE) are largely standard, every RDBMS adds proprietary extensions. Examples: (1) MySQL’s `AUTO_INCREMENT` for auto-generating primary keys vs. PostgreSQL’s `SERIAL` or SQL Server’s `IDENTITY`. (2) MySQL’s backtick (`) identifier quoting vs. standard double-quote (") used by PostgreSQL/Oracle. (3) MySQL’s `LIMIT` clause for pagination vs. standard `FETCH FIRST n ROWS ONLY` (or `TOP` in SQL Server). A student who agrees with the claim has not encountered dialect differences — a major pitfall in competitive exams where “write a query that works on any RDBMS” is a common constraint.

## DIAGNOSTIC_QUESTION_6
Design a minimal database schema (list the CREATE TABLE statements only) for a school library that tracks books and which student has borrowed which book. Include appropriate columns, data types, and indicate primary keys. Do not write foreign key constraints yet — just the table structures.

## DIAGNOSTIC_ANSWER_6
```sql
CREATE TABLE students (
    adm_no INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    class_sec VARCHAR(10) NOT NULL
);

CREATE TABLE books (
    book_id INT PRIMARY KEY,
    title VARCHAR(100) NOT NULL,
    author VARCHAR(50) NOT NULL,
    isbn CHAR(13) UNIQUE
);

CREATE TABLE borrowings (
    borrow_id INT PRIMARY KEY,
    adm_no INT NOT NULL,
    book_id INT NOT NULL,
    issue_date DATE NOT NULL,
    due_date DATE NOT NULL,
    return_date DATE
);
```
A poor answer might omit primary keys, use `VARCHAR` for `adm_no`, or forget `NOT NULL` on mandatory columns. This reveals inability to translate a real-world scenario into relational structure — the core competency for board case-study questions.

## COMMON_MISCONCEPTION
Students often think “SQL and MySQL are the same thing” and use the terms interchangeably. They write “MySQL query” when they mean “SQL query” and assume MySQL-specific features like `AUTO_INCREMENT`, `LIMIT`, or backtick quoting are part of the SQL standard. This happens because classroom instruction typically uses MySQL as the only RDBMS, so the boundary between language and implementation is never highlighted. In board exams, questions like “Identify the standard SQL clause for pagination” trip them up because they answer `LIMIT` (MySQL) instead of `FETCH FIRST` (standard). In JEE/CUET, they may be asked to spot the non-portable statement among options.

## WORKED_EXAMPLE_1
PROBLEM: A school wants to store details of its clubs. Each club has a unique numeric code (1-99), a name (up to 30 chars), a teacher-in-charge (up to 40 chars), and the number of student members (integer). Write the SQL commands to create a database `school_clubs`, a table `clubs` with appropriate data types, and insert three clubs: (10, 'Robotics', 'Ms. Sharma', 25), (20, 'Debate', 'Mr. Verma', 18), (30, 'Eco', 'Ms. Patel', 30).

STEPS:
- Step 1: Identify the entities and attributes — one table `clubs` with four columns: code, name, teacher, members.
- Step 2: Choose data types: code → INT (small range), name → VARCHAR(30), teacher → VARCHAR(40), members → INT.
- Step 3: Write CREATE DATABASE and USE statements to set the context.
- Step 4: Write CREATE TABLE with column definitions in the same order as the insert values.
- Step 5: Write three INSERT statements (or one multi-row INSERT) to populate the data.
- Step 6: Verify by describing the table and selecting all rows (though SELECT is in next node, we show it for completeness).
REASONING: The steps follow the lifecycle of database creation: container → structure → data. Choosing VARCHAR over CHAR for variable-length names saves space; INT for numeric codes enables numeric comparison and sorting later. Multi-row INSERT is standard SQL and more efficient.
ANSWER:
```sql
CREATE DATABASE school_clubs;
USE school_clubs;
CREATE TABLE clubs (
    code INT,
    name VARCHAR(30),
    teacher VARCHAR(40),
    members INT
);
INSERT INTO clubs VALUES
    (10, 'Robotics', 'Ms. Sharma', 25),
    (20, 'Debate', 'Mr. Verma', 18),
    (30, 'Eco', 'Ms. Patel', 30);
```

## WORKED_EXAMPLE_2
PROBLEM: The school’s sports department needs to record match results. Each match has a date, two team names (up to 25 chars each), and scores (integers). Design a table `matches` that can store this, ensuring the date and team names together uniquely identify a match (no two matches on same day with same teams). Write the CREATE TABLE statement using a composite primary key. Use MySQL syntax.

STEPS:
- Step 1: List columns: match_date (DATE), team_a (VARCHAR(25)), team_b (VARCHAR(25)), score_a (INT), score_b (INT).
- Step 2: Recognise that a single column cannot be primary key because multiple matches can occur on the same date; the combination (match_date, team_a, team_b) is unique.
- Step 3: In MySQL, define composite primary key at table level: PRIMARY KEY (match_date, team_a, team_b).
- Step 4: Choose DATE for match_date (enables date arithmetic), VARCHAR for team names, INT for scores.
- Step 5: Write the full CREATE TABLE statement with the composite primary key constraint.
REASONING: Composite primary keys are essential when no single column is a unique identifier. Using DATE (not VARCHAR) for dates allows range queries like "matches between two dates". VARCHAR(25) accommodates typical school team names.
ANSWER:
```sql
CREATE TABLE matches (
    match_date DATE,
    team_a VARCHAR(25),
    team_b VARCHAR(25),
    score_a INT,
    score_b INT,
    PRIMARY KEY (match_date, team_a, team_b)
);
```

## WORKED_EXAMPLE_3
PROBLEM: Extend the `participants` table from Diagnostic Question 3 to enforce that `pid` is a primary key, `name` cannot be NULL, `class` must be between 9 and 12, `phone` must be exactly 10 digits (use CHECK constraint), and `event` must be one of 'Dance', 'Music', 'Drama', 'Quiz', 'Sports'. Write the CREATE TABLE statement with all constraints. Use MySQL 8.0+ syntax.

STEPS:
- Step 1: Start from the basic column definitions in Diagnostic Question 3.
- Step 2: Add PRIMARY KEY constraint on `pid`.
- Step 3: Add NOT NULL on `name`.
- Step 4: Add CHECK constraint for `class`: CHECK (class BETWEEN 9 AND 12).
- Step 5: Add CHECK constraint for `phone`: CHECK (phone REGEXP '^[0-9]{10}$') — MySQL 8 supports REGEXP in CHECK.
- Step 6: Add CHECK constraint for `event`: CHECK (event IN ('Dance','Music','Drama','Quiz','Sports')).
- Step 7: Assemble the complete CREATE TABLE statement.
REASONING: Constraints move validation from application code into the database, guaranteeing data integrity. MySQL 8.0 finally enforces CHECK constraints (earlier versions ignored them). REGEXP ensures exactly 10 digits; IN list restricts events to a controlled vocabulary.
ANSWER:
```sql
CREATE TABLE participants (
    pid INT PRIMARY KEY,
    name VARCHAR(30) NOT NULL,
    class INT CHECK (class BETWEEN 9 AND 12),
    phone CHAR(10) CHECK (phone REGEXP '^[0-9]{10}$'),
    event VARCHAR(20) CHECK (event IN ('Dance','Music','Drama','Quiz','Sports'))
);
```

## COMPETENCY_QUESTION_1
QUESTION: A student writes the following commands in MySQL:
```sql
CREATE DATABASE test;
CREATE TABLE test.students (id INT, name VARCHAR(20));
INSERT INTO students VALUES (1, 'Aman');
```
The INSERT fails with “Error 1046: No database selected”. Explain why this happens and provide two different ways to fix it without changing the INSERT statement.

COMPETENCY: Error identification and correction in SQL environment/context management
STEPS:
- Step 1: Recognise that CREATE TABLE used a qualified name `test.students` but did not set the default database.
- Step 2: The INSERT uses an unqualified table name `students`, so MySQL looks in the current default database (which is still N/A).
- Step 3: Fix 1: Add `USE test;` before the INSERT.
- Step 4: Fix 2: Qualify the table in INSERT: `INSERT INTO test.students VALUES (1, 'Aman');` (but the problem says without changing INSERT, so this is not allowed; instead, the second fix is to run `USE test;` immediately after CREATE DATABASE, before CREATE TABLE).
- Step 5: Explain that `USE` sets the session’s default database; qualified names bypass the default but unqualified names require it.
ANSWER: The INSERT fails because no default database is selected. The CREATE TABLE used a fully qualified name `test.students`, which creates the table in database `test` but does not change the current database context. The subsequent unqualified `INSERT INTO students` therefore has no target database. Two fixes: (1) Execute `USE test;` before the INSERT (or right after CREATE DATABASE). (2) Change the CREATE TABLE to `CREATE TABLE students ...` after `USE test;` so the table is created in the current database and the INSERT works as written.
DIFFICULTY: medium

## COMPETENCY_QUESTION_2
QUESTION: A school’s fee management system stores student fee records in a table `fees` with columns `adm_no` (INT), `term` (VARCHAR(10) — values like 'Term1', 'Term2'), `amount` (DECIMAL(10,2)), `paid_date` (DATE). The school wants to ensure: (a) a student cannot have two records for the same term, (b) amount is positive, (c) paid_date is not in the future. Write a single CREATE TABLE statement for MySQL 8.0 that implements all these rules using appropriate constraints. Also explain why DECIMAL(10,2) is preferred over FLOAT for the amount column.

COMPETENCY: Translating real-world business rules into declarative database constraints; numeric type selection for monetary data
STEPS:
- Step 1: Identify primary key: composite (adm_no, term) ensures one record per student per term.
- Step 2: Add CHECK constraint for positive amount: CHECK (amount > 0).
- Step 3: Add CHECK constraint for paid_date not in future: CHECK (paid_date <= CURDATE()) — MySQL allows non-deterministic functions in CHECK from 8.0.16? Actually MySQL does not allow CURDATE() in CHECK (it’s non-deterministic). Alternative: use a trigger or application logic. But for board exam, they might accept CHECK (paid_date <= '2099-12-31') as a placeholder. We'll note the limitation.
- Step 4: Choose DECIMAL(10,2) for exact decimal representation; FLOAT is approximate binary floating-point and can cause rounding errors in financial calculations (e.g., 0.1 + 0.2 != 0.3).
- Step 5: Write the CREATE TABLE with composite PRIMARY KEY and two CHECK constraints (amount, paid_date with a fixed far-future date as a pragmatic workaround).
REASONING: Constraints declaratively enforce business rules at the database level. DECIMAL stores exact base-10 values, critical for money; FLOAT’s binary representation leads to tiny discrepancies that accumulate in sums and reports — a classic trap in both board exams (theory) and competitive exams (numerical output questions).
ANSWER:
```sql
CREATE TABLE fees (
    adm_no INT,
    term VARCHAR(10),
    amount DECIMAL(10,2) CHECK (amount > 0),
    paid_date DATE CHECK (paid_date <= '2099-12-31'),
    PRIMARY KEY (adm_no, term)
);
```
Note: MySQL 8.0 does not allow `CURDATE()` in CHECK constraints; a trigger or application-layer check is needed for real future-date prevention. The fixed date is a pragmatic placeholder for exam purposes.
