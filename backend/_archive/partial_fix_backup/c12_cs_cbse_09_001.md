## DEFINITION
A function in Python is a named, reusable block of code that performs a specific task, accepts zero or more input values (parameters), and optionally returns a result; it enables modular programming by encapsulating logic so it can be called multiple times from different parts of a program without rewriting code.

## WALKTHROUGH
Imagine you run a small bakery and need to calculate the final price (base price + 18% GST) for 20 different items every day. Without functions, you would write the same calculation 20 times — if the GST rate changes, you must edit 20 places. A function lets you write the logic once, give it a name like `calculate_final_price`, and reuse it for every item. Start by asking: "What task do I repeat?" Then identify inputs (base price) and output (final price). The key insight is that a function is a **named recipe** — you write the steps once, then just say the name whenever you need the dish.

## DIAGNOSTIC_QUESTION_1
What is the primary purpose of a function in Python, and how does it differ from simply writing the same code multiple times?

## DIAGNOSTIC_ANSWER_1
A function encapsulates a specific task into a named, reusable unit that can be called with different inputs, avoiding code duplication. A wrong answer (e.g., "functions make code run faster" or "functions are only for math") reveals the student confuses functions with performance optimization or mathematical functions, missing the core idea of **abstraction and reuse**.

## DIAGNOSTIC_QUESTION_2
Explain in your own words why "modularity" is an advantage of functions, using a real-life analogy (not a coding example).

## DIAGNOSTIC_ANSWER_2
Modularity means breaking a complex problem into independent, manageable pieces — like a kitchen where separate chefs handle starters, mains, and desserts. Each chef (function) has a clear job, can be replaced or improved without disturbing others, and the head chef (main program) just coordinates. A wrong answer that only says "code becomes shorter" misses the **independence and isolation** aspect — modularity is about structure, not just length.

## DIAGNOSTIC_QUESTION_3
A student writes a 50-line script to process student marks: it reads input, calculates average, assigns grade, and prints a report — all in one block. They want to reuse the grade-calculation logic for another class. How would using a function help? Write the function signature (name and parameters only) for the grade calculation.

## DIAGNOSTIC_ANSWER_3
A function `calculate_grade(average: float) -> str` isolates the grading logic so it can be called from anywhere with just the average as input. The student avoids copying 10 lines of if-elif chains. A wrong answer that suggests copying the code block or using a loop shows they don't grasp **parameterization and single-responsibility** — the function should do ONE thing (grade from average) and take exactly what it needs.

## DIAGNOSTIC_QUESTION_4
Compare built-in functions (e.g., `len()`, `print()`) and user-defined functions. What is the key similarity and the key difference in how a programmer interacts with them?

## DIAGNOSTIC_ANSWER_4
Similarity: both are called by name with parentheses and arguments, and both return a value (or `N/A`). Difference: built-ins are pre-written by Python developers; user-defined functions are written by **you** for your specific problem. A wrong answer like "built-ins are faster" or "user-defined functions can't return values" reveals confusion about **origin vs. capability** — both can do the same things; the difference is who wrote them and for what purpose.

## DIAGNOSTIC_QUESTION_5
A team of three students is building a library management system. One writes the "book search" logic, another writes "issue book", another writes "return book". They decide to put all code in one giant function `run_library()`. Evaluate this design decision. What specific problems will arise?

## DIAGNOSTIC_ANSWER_5
This violates modularity: (1) merge conflicts when editing the same function, (2) no reuse — search logic can't be used without running issue/return, (3) debugging is harder — a bug in "return" breaks everything, (4) testing is impossible in isolation. A good evaluation identifies **at least two** of these with reasoning. A weak answer ("it's messy") lacks specificity — the student must articulate **why** monolithic functions hurt collaboration and maintenance.

(d) Fare rules change (base fare, per-km rate, night surcharge) — a function `calculate_fare(distance_km: float, is_night: bool = False) -> float` centralizes logic so updates happen in one place. ## COMMON_MISCONCEPTION
Students think a function is **only** for mathematical calculations (like `f(x) = x²`) because math classes use that terminology. In Python, a function can do **anything** — print a menu, write to a file, draw a chart, send an email — and may not return a value at all. They write `def greet(): print("Hello")` and ask "where is the return?" not realizing `N/A` is a valid return. This stems from conflating **mathematical function** (input→output mapping) with **programming function** (named code block with side effects).

## WORKED_EXAMPLE_1
PROBLEM: A school canteen sells three items: samosa (₹15), sandwich (₹40), and juice (₹25). The accountant manually calculates the total for each student's order by multiplying quantity × price and summing. Design a function to automate this. Identify the task, inputs, output, and write the function signature. Explain why this is better than doing it inline for each student.

STEPS:
- Step 1: Identify the repeated task — computing order total from quantities of fixed-price items.
- Step 2: Determine inputs — three integers: qty_samosa, qty_sandwich, qty_juice.
- Step 3: Determine output — one integer: total_amount in rupees.
- Step 4: Write function signature — `def calculate_order_total(qty_samosa: int, qty_sandwich: int, qty_juice: int) -> int:`
- Step 5: Explain advantage — prices are in ONE place; if samosa price changes to ₹18, update only the function body, not every student's calculation.

REASONING: The function encapsulates the pricing logic (the "rule") so the main program only needs to pass quantities. This separates **what** (prices) from **how** (multiplication and addition), making the code maintainable and reusable for 500+ students daily.

ANSWER: Function signature: `calculate_order_total(qty_samosa: int, qty_sandwich: int, qty_juice: int) -> int`. Advantage: single point of price maintenance, reusable for any number of orders, readable main code.

## WORKED_EXAMPLE_2
PROBLEM: A teacher wants to convert marks (0–100) to grades: 90+ = 'A', 75–89 = 'B', 60–74 = 'C', 40–59 = 'D', below 40 = 'F'. She currently uses a long if-elif chain in her main script for each student. Design a function to handle this. Specify inputs, output, signature, and two advantages over inline code.

STEPS:
- Step 1: Identify the task — mapping a numeric mark to a letter grade based on fixed thresholds.
- Step 2: Input — one integer `marks` (0–100). Output — one string `grade` ('A'–'F').
- Step 3: Write signature — `def marks_to_grade(marks: int) -> str:`
- Step 4: Advantage 1 — if grading policy changes (e.g., 85+ = 'A'), edit only this function, not every student's block.
- Step 5: Advantage 2 — the main script becomes cleaner: `grade = marks_to_grade(student_marks)` instead of 10 lines of conditions.

REASONING: The function isolates the **grading policy** (business logic) from the **data processing loop** (control flow). This is separation of concerns: the loop shouldn't know grade boundaries; it should only ask "what grade for this mark?"

ANSWER: Signature: `marks_to_grade(marks: int) -> str`. Advantages: (1) Policy changes localized to one function. (2) Main code readability — intent is clear from function name.

## WORKED_EXAMPLE_3
PROBLEM: A delivery startup calculates shipping cost: base ₹50 for first 2 km, then ₹15 per additional km. They also offer a "prime" membership giving 20% discount on the final cost. Write a function `shipping_cost(distance_km: float, is_prime: bool = False) -> float` that computes the cost. Show how this function would be used for three customers: (a) 1.5 km, non-prime, (b) 5 km, prime, (c) 10 km, non-prime. Explain how the default parameter `is_prime=False` supports reusability.

STEPS:
- Step 1: Understand the pricing rule — piecewise: base + extra for distance > 2 km.
- Step 2: Define function with parameters: distance (float), is_prime (bool, default False).
- Step 3: Write logic: if distance <= 2: cost = 50; else: cost = 50 + 15 * (distance - 2).
- Step 4: Apply discount if is_prime: cost *= 0.8.
- Step 5: Return cost.
- Step 6: Call for three cases: (a) shipping_cost(1.5) → 50.0; (b) shipping_cost(5, True) → (50 + 15*3)*0.8 = 95*0.8 = 76.0; (c) shipping_cost(10) → 50 + 15*8 = 170.0.
- Step 7: Explain default parameter — most customers are non-prime, so callers can omit the second argument; prime customers pass `True`. This avoids two separate functions.

REASONING: The function handles **variability** (distance, membership) through parameters and defaults. The piecewise logic is centralized. Default parameter reduces caller burden for the common case (non-prime), demonstrating **design for usability** — a key advantage of well-designed functions.

ANSWER: Function computes correctly for all cases. Default parameter allows `shipping_cost(5)` for non-prime and `shipping_cost(5, True)` for prime — one function serves both, avoiding code duplication.

## COMPETENCY_QUESTION_1
QUESTION: A Class 12 student writes a program to generate a multiplication table for a given number `n` from 1 to 10. They write the print statements directly in a loop inside `main()`. Their teacher suggests making a function `print_table(n: int) -> N/A`. The student argues: "It works fine as is. Why add a function?" 

Give **three distinct reasons** why the function version is better, each tied to a specific advantage of functions (modularity, reusability, readability, maintainability, or abstraction). For each reason, describe a concrete scenario where the inline version would cause trouble.

COMPETENCY: Translating real-world situations to mathematical expressions / Comparing and justifying design choices

STEPS:
- Step 1: Identify the core task — printing a multiplication table for any number.
- Step 2: List advantages of function version over inline loop.
- Step 3: For each advantage, create a concrete "what if" scenario where inline fails.
- Step 4: Map each scenario to the named advantage.

ANSWER: 
1. **Reusability**: If the teacher asks "print tables for 2 to 12", inline code must be copied 11 times; function version just loops `for i in range(2,13): print_table(i)`.
2. **Maintainability**: If format changes to "2 × 3 = 6" (with × and =), inline version needs edits in 11 places; function version changes once.
3. **Abstraction/Readability**: Main code becomes `print_table(7)` — intent is obvious. Inline version buries the logic inside a larger script, forcing readers to parse the loop to understand its purpose.

## COMPETENCY_QUESTION_2
QUESTION: A team is building a GST billing module for a shop. They have two design options:

**Option A**: One function `generate_bill(items: list[dict]) -> float` that takes a list of items (each with name, price, qty, gst_rate), calculates everything, prints the bill, and returns total.

**Option B**: Three functions:
- `calculate_item_total(price: float, qty: int, gst_rate: float) -> float`
- `calculate_bill_total(items: list[dict]) -> float` (uses the above)
- `print_bill(items: list[dict], total: float) -> N/A`

Evaluate both designs. Which follows the **single responsibility principle** better? What specific problems will Option A cause when: (i) GST rates change for only some items, (ii) the shop wants to email bills instead of printing, (iii) a unit test needs to verify only the calculation logic?

COMPETENCY: Error identification and correction / Comparing and justifying

STEPS:
- Step 1: Define single responsibility principle — a function should do one thing well.
- Step 2: Analyze Option A — does calculation, formatting, printing, and I/O all in one.
- Step 3: Analyze Option B — each function has one clear job.
- Step 4: For each scenario (i, ii, iii), explain why Option A fails and Option B succeeds.

ANSWER: 
**Option B** follows single responsibility better. 
(i) GST rate change for some items: Option A requires editing the monolithic function and risks breaking printing; Option B only touches `calculate_item_total`.
(ii) Email instead of print: Option A mixes calculation with print — must rewrite the whole function; Option B just replaces `print_bill` with `email_bill`, reusing calculation functions.
(iii) Unit test calculation only: Option A forces test to capture printed output or mock stdout; Option B tests `calculate_item_total` and `calculate_bill_total` directly with assertions.

DIFFICULTY: hard
