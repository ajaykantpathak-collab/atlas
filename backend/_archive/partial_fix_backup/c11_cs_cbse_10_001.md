## DEFINITION
A data structure is a specialized format for organizing, processing, retrieving, and storing data in computer memory so that it can be accessed and modified efficiently; it defines the logical relationship between data elements and the operations permitted on them.

## WALKTHROUGH
Imagine you are building a music playlist app: you need to add songs, play the most recently added song first (like a stack), or play songs in the order they were added (like a queue). How do you decide which internal structure to use? We begin by asking: what operations will be frequent—insert at end, delete from front, search by name? This leads to the core idea: a data structure is not just storage; it is a contract between how data is laid out in memory and which operations are fast. We then classify structures by shape (linear: one-after-another vs non-linear: branching) and by memory behaviour (static: fixed size vs dynamic: grow/shrink). The key insight is that every choice trades off speed of one operation against another—there is no universally "best" structure, only the best fit for a specific access pattern.

## DIAGNOSTIC_QUESTION_1
Define "data structure" in your own words and give one example of a linear and one example of a non-linear data structure.

## DIAGNOSTIC_ANSWER_1
A data structure is a way of organizing data in memory so that specific operations (insert, delete, search, traverse) can be performed efficiently; it specifies the logical relationship among elements and the allowed operations. Linear example: Array (or Stack, Queue, List) where elements form a sequence. Non-linear example: Tree (or Graph) where elements have hierarchical or network relationships. A wrong answer that only says "it stores data" reveals the student misses the critical link between organization and operation efficiency; an answer that confuses "array" (implementation) with "stack" (abstract data type) reveals confusion between concrete and abstract views.

## DIAGNOSTIC_QUESTION_2
Explain why a Python list is considered a dynamic data structure while a C-style array is static, and describe one situation where you would deliberately choose a static structure over a dynamic one.

## DIAGNOSTIC_ANSWER_2
A Python list automatically resizes (allocates a larger block, copies elements) when capacity is exceeded, so its size can grow or shrink at runtime; a C-style array has fixed size allocated at compile time and cannot change. You would choose a static structure when memory is extremely constrained (embedded systems), when maximum size is known and fixed (e.g., a 3x3 tic-tac-toe board), or when predictable O(1) access without resizing overhead is critical. A wrong answer that claims "lists are dynamic because they use pointers" shows confusion between implementation mechanism and abstract property; an answer that cannot name a valid use-case for static structures reveals lack of understanding of trade-offs.

## DIAGNOSTIC_QUESTION_3
A school wants to maintain a record of students waiting to see the principal. Students join the line at the end and are called from the front. Which abstract data type (Stack or Queue) models this situation? Justify your answer by naming the principle (LIFO/FIFO) and the two primary operations with their standard names.

## DIAGNOSTIC_ANSWER_3
Queue models this situation because it follows FIFO (First-In-First-Out): the student who arrives first is served first. Primary operations: enqueue (insert at rear) and dequeue (remove from front). A wrong answer choosing Stack reveals the student confuses "last added served first" (LIFO) with real-world queues; an answer that names operations as "push/pop" instead of "enqueue/dequeue" shows terminology confusion between the two ADTs.

## DIAGNOSTIC_QUESTION_4
Compare the time complexity of searching for an element in an unsorted array versus a binary search tree (BST) in the average case. Explain why the BST is not always faster despite its better asymptotic complexity.

## DIAGNOSTIC_ANSWER_4
Unsorted array: O(n) linear search; balanced BST: O(log n) average case. BST is not always faster because: (1) it requires the tree to be balanced—degenerate BST becomes O(n); (2) BST has higher constant factors (pointer chasing, cache misses) making it slower for small n; (3) BST needs extra memory for pointers; (4) if data is static and searched often, sorting the array once (O(n log n)) then binary search (O(log n)) beats BST construction overhead. A wrong answer stating "BST is always faster because log n < n" ignores constants, balance requirement, and memory hierarchy effects.

## DIAGNOSTIC_QUESTION_5
Evaluate the claim: "Since Python lists can grow dynamically and support insert/delete at any index, there is no need to learn Stack or Queue as separate data structures." Provide two technical counterarguments.

## DIAGNOSTIC_ANSWER_5
Counterargument 1: Abstraction barrier—Stack/Queue restrict operations (only push/pop or enqueue/dequeue) preventing accidental misuse (e.g., inserting in middle of a call stack would break recursion). Counterargument 2: Performance contract—Stack/Queue guarantee O(1) for their specific operations; Python list insert/delete at front is O(n) due to shifting, so using a list as a queue without collections.deque violates the expected complexity. A wrong answer focusing only on "code readability" misses the computational complexity and correctness guarantees that define an Abstract Data Type.

## DIAGNOSTIC_QUESTION_6
Design a minimal data structure to implement an "undo" feature in a text editor that supports only two operations: type(character) and undo(). Specify the ADT, the underlying concrete structure, and the exact algorithm for each operation in pseudocode.

## DIAGNOSTIC_ANSWER_6
ADT: Stack (LIFO). Concrete: Dynamic array (Python list) or singly linked list. Algorithm: type(c): push(c) onto stack. undo(): if stack not empty: pop() and remove last character from document; else: ignore. A good answer explicitly states LIFO property matches "last action undone first", names push/pop, and handles empty-stack edge case. A poor answer uses a queue (wrong order), omits the empty check, or suggests storing entire document snapshots (space inefficient) revealing misunderstanding of incremental state capture.

## COMMON_MISCONCEPTION
Students often believe "data structure" and "data type" are synonyms, and that Python's list is a "universal" structure eliminating the need for Stack, Queue, or Linked List. They write code like `my_stack = []` and use `insert(0, x)` for push and `pop(0)` for pop, thinking this is a stack. This is wrong because: (1) list `insert(0, x)` and `pop(0)` are O(n) due to shifting all elements, violating the Stack ADT's O(1) push/pop contract; (2) the list exposes operations (insert at middle, slice, sort) that a Stack should forbid, breaking encapsulation; (3) they confuse the *interface* (ADT) with *implementation* (list). The root cause is treating data structures as mere syntax rather than as behavioural contracts with complexity guarantees.

## ON_FAILURE
Step 1: Show the student a timing experiment—run `push`/`pop` at end of list (O(1)) vs `insert(0)`/`pop(0)` at front (O(n)) for n=100,000 and display the 1000x slowdown. Step 2: Ask them to implement a function `is_balanced(parentheses_string)` using only `append` and `pop` (end of list) to enforce LIFO discipline. Step 3: Have them write a `Stack` class that wraps a list but *only* exposes `push`, `pop`, `peek`, `is_empty`—hide the underlying list. Step 4: Explain that the *interface* (what operations exist) and *complexity promise* (how fast they are) together define the ADT; Python list is just one possible implementation, not the ADT itself.

## WORKED_EXAMPLE_1
PROBLEM: A library stores book records in a system. Each record has: Accession Number (unique integer), Title (string), Author (string), Status (Available/Issued). The librarian frequently needs to: (a) find a book by accession number, (b) list all books by a given author, (c) add new books, (d) remove lost books. Recommend whether a linear or non-linear data structure is more suitable. Justify with time complexities for each operation.

STEPS:
- Step 1: Identify the access patterns: (a) is exact-key lookup, (b) is search by non-key attribute, (c) and (d) are dynamic updates.
- Step 2: Compare linear structures (array/list): lookup by accession requires O(n) linear search unless sorted (then O(log n) binary search but insert/delete become O(n) due to shifting). Search by author always O(n).
- Step 3: Compare non-linear structures: Hash table (dictionary) on accession gives O(1) average lookup; secondary index (author → list of accessions) gives O(1) + O(k) for author search. Balanced BST on accession gives O(log n) for all.
- Step 4: Evaluate trade-offs: Hash table best for primary key ops; author search needs auxiliary structure. Since accession is unique and primary, hash table (non-linear) is superior.
- Step 5: Conclude: Non-linear (hash table/dictionary) is recommended for O(1) accession lookup and O(1) insert/delete; maintain a separate dictionary mapping author to list of accessions for author search.

REASONING: The problem requires frequent exact-key lookup and dynamic updates—hash tables (non-linear) provide constant-time average case for these, while linear structures require O(n) or O(log n) with shifting overhead. The multi-attribute search (author) is handled by an auxiliary index, a standard database technique.

ANSWER: Non-linear data structure (Hash Table / Dictionary) keyed by Accession Number for O(1) average lookup, insert, delete; auxiliary Dictionary mapping Author → List of Accessions for O(1) + O(k) author search.

## WORKED_EXAMPLE_2
PROBLEM: A traffic light controller cycles through Red → Green → Yellow → Red repeatedly. The system must store the sequence of states and support: (1) get current state, (2) advance to next state, (3) reset to Red. The cycle never changes. Choose between static array, dynamic list, and circular linked list. Justify with memory and time analysis.

STEPS:
- Step 1: Note the sequence is fixed (3 states), known at compile time, and cycles infinitely.
- Step 2: Static array: stores 3 elements, fixed memory, O(1) access by index. Current state = array[index]. Advance = index = (index + 1) % 3. Reset = index = 0. All O(1), no allocation after init.
- Step 3: Dynamic list: same operations but carries resizing overhead (capacity, growth factor) unnecessary for fixed 3 elements.
- Step 4: Circular linked list: 3 nodes with next pointers forming a loop. Advance = current = current.next (O(1)). But extra pointer memory per node (3 pointers) and cache-unfriendly non-contiguous allocation.
- Step 5: Conclude: Static array is optimal—smallest memory (no pointers, no capacity buffer), best cache locality, simplest code, guaranteed O(1) for all ops.

REASONING: When size is fixed and known, static arrays eliminate dynamic allocation overhead, pointer overhead, and cache misses. The modulo arithmetic for cycling is a classic constant-time technique.

ANSWER: Static array of size 3 with integer index and modulo-3 arithmetic for cycling. Memory: 3 × state_size bytes. All operations O(1) with zero allocation after initialization.

## WORKED_EXAMPLE_3
PROBLEM: An e-commerce site shows "Recently Viewed Products" (max 20 items). When a user views a product: if already in list, move it to front; else add to front; if list exceeds 20, remove last. The site also needs "Clear History" and "Get item at position k (1=most recent)". Design the data structure with all operations in O(1) or O(k) time. Provide class skeleton with method signatures and complexity comments.

STEPS:
- Step 1: Analyze operations: move-to-front, add-to-front, remove-last, clear, get-at-k. This is a "move-to-front" list with fixed capacity—similar to LRU cache.
- Step 2: Singly linked list with head/tail pointers: add-to-front O(1), remove-last O(n) (need previous node) — fails.
- Step 3: Doubly linked list with head/tail: add-to-front O(1), move-to-front (unlink + relink) O(1), remove-last O(1), clear O(1) (drop head), get-at-k O(k) traversal from head.
- Step 4: Add dictionary mapping product_id → node for O(1) "is already in list" check.
- Step 5: Write class skeleton with Node (prev, next, product_id), DLL with head, tail, size, capacity, and dict. Methods: view(product_id), get(k), clear().
- Step 6: Annotate each method with time complexity and explain why doubly linked list + hash map achieves all requirements.

REASONING: The combination of doubly linked list (O(1) insertion/deletion at both ends and middle given node reference) and hash map (O(1) node lookup) is the standard LRU cache structure. Capacity limit makes it a bounded structure.

ANSWER:
```python
class Node:
    def __init__(self, pid):
        self.pid = pid
        self.prev = None
        self.next = None

class RecentlyViewed:
    def __init__(self, capacity=20):
        self.cap = capacity
        self.size = 0
        self.head = None  # most recent
        self.tail = None  # least recent
        self.map = {}     # pid -> Node

    # O(1) average
    def view(self, pid):
        if pid in self.map:
            node = self.map[pid]
            self._unlink(node)
            self._add_to_front(node)
        else:
            node = Node(pid)
            self.map[pid] = node
            self._add_to_front(node)
            self.size += 1
            if self.size > self.cap:
                self._remove_last()

    # O(k)
    def get(self, k):
        if k < 1 or k > self.size: return None
        cur = self.head
        for _ in range(k-1):
            cur = cur.next
        return cur.pid

    # O(1)
    def clear(self):
        self.head = self.tail = None
        self.size = 0
        self.map.clear()

    def _add_to_front(self, node):
        node.next = self.head
        node.prev = None
        if self.head: self.head.prev = node
        self.head = node
        if self.tail is None: self.tail = node

    def _unlink(self, node):
        if node.prev: node.prev.next = node.next
        else: self.head = node.next
        if node.next: node.next.prev = node.prev
        else: self.tail = node.prev

    def _remove_last(self):
        if self.tail:
            del self.map[self.tail.pid]
            self._unlink(self.tail)
            self.size -= 1
```
Complexities: view O(1), get O(k), clear O(1).

## COMPETENCY_QUESTION_1
QUESTION: A student writes a `Stack` class using a Python list but implements `push` as `self.items.insert(0, item)` and `pop` as `self.items.pop(0)`. (a) State the time complexity of each operation. (b) Explain why this violates the Stack ADT contract. (c) Rewrite both methods to achieve the correct complexity using only list methods.

COMPETENCY: Error identification and correction with complexity analysis

STEPS:
- Step 1: Recognize that `insert(0, item)` shifts all existing elements right → O(n). `pop(0)` shifts all elements left → O(n).
- Step 2: Stack ADT requires push and pop to be O(1) because they operate only at the "top" (one end). Using the front of a list as top forces shifting.
- Step 3: Use the *end* of the list as the top: `push` → `self.items.append(item)` (amortized O(1)), `pop` → `self.items.pop()` (O(1)).
- Step 4: Verify that `append`/`pop` at end do not shift elements and match LIFO semantics.

ANSWER: (a) Both operations are O(n) due to element shifting. (b) Stack ADT guarantees O(1) push and pop; the implementation breaks this performance contract and also exposes the wrong end as "top" conceptually. (c) `push`: `self.items.append(item)`; `pop`: `return self.items.pop()` (with empty check). Both are O(1) amortized.

## COMPETENCY_QUESTION_2
QUESTION: A game engine stores active projectiles (bullets, arrows) in a data structure. Each frame: new projectiles are spawned (added), expired projectiles are removed, and all projectiles are updated (position += velocity). The maximum projectiles is 500. Compare these three designs for the projectile container: (A) Python list, (B) Fixed-size array with "active" boolean flag per slot, (C) Doubly linked list. For each, state the time complexity of spawn, expire (given reference), and update-all. Recommend the best for a 60 FPS game and justify.

COMPETENCY: Comparing and justifying data structure choices for real-time systems

STEPS:
- Step 1: Design A (Python list): spawn `append` O(1) amortized; expire requires search O(n) + `pop(index)` O(n) shift; update-all O(n) contiguous traversal (cache-friendly).
- Step 2: Design B (Fixed array + flags): spawn scans for inactive slot O(500)=O(1) bounded; expire given index O(1) (clear flag); update-all scans all 500 slots O(500)=O(1) but checks flag each iteration.
- Step 3: Design C (Doubly linked list): spawn `add_to_front` O(1); expire given node reference O(1) unlink; update-all O(n) but pointer-chasing hurts cache.
- Step 4: For 60 FPS (16.6ms/frame), predictable O(1) bounded operations matter more than asymptotic. Design B has zero allocation after init, no GC pressure, contiguous memory, and deterministic 500-iteration loop—ideal for real-time.
- Step 5: Recommend Design B with object pooling pattern.

ANSWER: Design B (fixed array with active flags) is best: spawn O(1) bounded scan, expire O(1), update-all O(500) deterministic with perfect cache locality and zero runtime allocation. Design A has O(n) expire and GC spikes; Design C has cache misses from pointer chasing.
