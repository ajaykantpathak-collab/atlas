## DEFINITION
The World Wide Web (Web) is a global information system of interlinked hypertext documents and resources accessed via the Internet using HTTP/HTTPS protocols. Web 2.0 represents the evolutionary shift from static, read-only websites (Web 1.0) to dynamic, interactive platforms enabling user-generated content, collaboration, and rich media experiences through technologies like AJAX, APIs, and social networking features.

## WALKTHROUGH
Imagine you are comparing two Indian railway ticketing experiences: the old IRCTC website from 2005 where you could only view static timetables and had to call a call center to book, versus the current IRCTC platform where you log in, see personalized recommendations, book tickets in real-time with live seat availability, and share your journey on social media. Start by asking: "What changed between these two versions?" Guide students to list differences: static vs dynamic content, one-way vs two-way communication, isolated vs social features. Then introduce the terms Web 1.0 and Web 2.0 as labels for these eras. Explain that Web 2.0 is not a new technology but a paradigm shift enabled by existing technologies (HTML, CSS, JavaScript, server-side languages, databases) used in new ways — especially AJAX for asynchronous updates and APIs for service integration. Conclude with the key insight: Web 2.0 turns users from passive consumers into active participants, creating network effects that drive platform value.

## DIAGNOSTIC_QUESTION_1
State whether the following is true or false: "Web 2.0 is a separate technical protocol that replaced HTTP." 

## DIAGNOSTIC_ANSWER_1
False. Web 2.0 is not a protocol; it is a design philosophy and set of practices that use existing protocols (HTTP/HTTPS) to enable interactivity, user-generated content, and rich interfaces. A wrong answer reveals the student confuses the *application layer paradigm* with the *transport protocol*, a common category error that leads to misunderstanding why Web 2.0 sites still use standard URLs and browsers.

## DIAGNOSTIC_QUESTION_2
A student claims: "Google Search is a Web 1.0 service because it only shows links to other pages." Explain why this classification is incorrect, referencing at least two Web 2.0 characteristics Google exhibits.

## DIAGNOSTIC_ANSWER_2
Google Search is a Web 2.0 service because (1) it heavily relies on user-generated data (clicks, links, behavior) to improve rankings via PageRank and machine learning — a hallmark of collective intelligence, and (2) it offers rich interactive features like autocomplete, instant results, and personalized search history, all powered by AJAX and real-time server communication. A wrong answer shows the student equates "showing links" with static content, missing that the *backend intelligence* and *frontend interactivity* are Web 2.0 hallmarks.

## DIAGNOSTIC_QUESTION_3
Consider an Indian e-commerce site that displays product pages with fixed HTML, requires full page reload for every category change, and has no user reviews or wishlist. The company wants to add: (a) live price updates via AJAX, (b) user reviews with ratings, (c) a "Share on WhatsApp" button. For each feature, identify whether it represents a Web 2.0 characteristic and name the enabling technology.

## DIAGNOSTIC_ANSWER_3
(a) Live price updates → Web 2.0 characteristic: **Real-time interactivity / Asynchronous communication**; Enabling technology: **AJAX (XMLHttpRequest/Fetch API)**. (b) User reviews → Web 2.0 characteristic: **User-generated content / Collective intelligence**; Enabling technology: **Server-side scripting (PHP/Python/Node.js) + Database (MySQL/MongoDB)**. (c) Share on WhatsApp → Web 2.0 characteristic: **Social integration / Platform openness**; Enabling technology: **Web APIs (WhatsApp Business API / URL schemes)**. A wrong answer (e.g., attributing live updates to "HTML5" or reviews to "CSS") reveals confusion between *presentation* and *data-driven interaction* layers.

## DIAGNOSTIC_QUESTION_4
Compare the architecture of a traditional Web 1.0 blog (static HTML files served directly) with a Web 2.0 blog platform (like WordPress). Analyze how the **data flow**, **user role**, and **scalability challenges** differ between the two.

## DIAGNOSTIC_ANSWER_4
| Aspect | Web 1.0 Blog | Web 2.0 Blog Platform |
|--------|--------------|------------------------|
| **Data Flow** | Server → Client only (one-way). Files are pre-written HTML. | Bidirectional: Client sends data (comments, posts) → Server processes → Database stores → Server dynamically generates HTML → Client. |
| **User Role** | Passive reader. No authentication needed. | Active participant: author, commenter, subscriber. Requires authentication, sessions, roles. |
| **Scalability** | Easy: static files can be cached/CDN-served. Hard to update content globally. | Harder: dynamic queries, session state, database writes. Requires caching layers, load balancing, database optimization. |
A wrong answer that says "Web 2.0 is just more HTML" misses the fundamental shift to **application logic + persistent state** on the server.

## DIAGNOSTIC_QUESTION_5
Evaluate this claim: "Web 2.0 eliminated the need for HTML because everything is now built with JavaScript frameworks like React." Provide a reasoned judgment with technical justification.

## DIAGNOSTIC_ANSWER_5
The claim is **false**. JavaScript frameworks (React, Vue, Angular) ultimately **produce HTML** that the browser renders. HTML remains the universal markup language understood by all browsers; frameworks just generate it programmatically. Moreover, semantic HTML is critical for accessibility (screen readers), SEO, and progressive enhancement. A wrong answer reveals the student conflates *authoring tools* with *output format* — a dangerous misconception that leads to inaccessible, poorly indexed web applications.

## DIAGNOSTIC_QUESTION_6
Design a minimal Web 2.0 feature for a school library website: students can reserve books online and receive notifications. Sketch the **client-side interactions**, **server-side endpoints**, and **data entities** needed. Assume the school uses a MySQL database and a Python (Flask) backend.

## DIAGNOSTIC_ANSWER_6
**Client-side**: (1) Login page (form → POST /login), (2) Book search (AJAX GET /api/books?q=...), (3) Reserve button (AJAX POST /api/reserve {book_id}), (4) Notification bell icon (periodic AJAX GET /api/notifications).  
**Server endpoints**: POST /login, GET /api/books, POST /api/reserve, GET /api/notifications, PUT /api/notifications/read.  
**Data entities**: `User(id, name, class, password_hash)`, `Book(id, title, author, copies_total, copies_available)`, `Reservation(id, user_id, book_id, status, timestamp)`, `Notification(id, user_id, message, is_read, timestamp)`.  
A poor answer that puts all logic in HTML/JS (no server, no database) shows the student hasn't grasped the **client-server-data triad** essential to Web 2.0.

## COMMON_MISCONCEPTION
Students often think "Web 2.0 = using JavaScript" or "Web 2.0 = fancy animations." They write in exams: "Web 2.0 websites use JavaScript, Web 1.0 don't." This is wrong because: (1) Web 1.0 sites *did* use JavaScript (for rollovers, form validation) — but only for client-side UI effects, not for server communication. (2) Web 2.0's defining trait is **architectural**: bidirectional data flow, persistent user state, and user-as-contributor — enabled by AJAX, server-side sessions, and databases. A site with beautiful animations but no user accounts, no dynamic data, and no social features is still Web 1.0. This misconception costs marks in board questions asking to "justify whether a given site is Web 2.0" and in competitive exams where architecture questions test the *data flow* not the *visuals*.

## ON_FAILURE
If a student exhibits this misconception:  
1. Show two code snippets: a 2003-era JS image rollover (Web 1.0) vs a modern `fetch('/api/like', {method:'POST'})` (Web 2.0). Ask: "Which one changes server state?"  
2. Have them trace the **HTTP request/response cycle** for both — emphasize that Web 2.0 requires *stateful server interactions* (cookies, tokens, DB writes).  
3. Assign a micro-task: "Add a 'like' button to a static HTML page using only client-side JS." They'll realize they cannot persist likes without a server.  
4. Re-diagnose with a question: "A site uses React but serves fully static HTML from a CDN with no backend API. Is it Web 2.0? Why/why not?" Correct answer: No — no server-side state mutation, no user-generated content persistence.

## WORKED_EXAMPLE_1
PROBLEM: An Indian NGO runs a static website (Web 1.0) showing their projects, contact info, and donation details as fixed HTML pages. They want to migrate to Web 2.0 to enable: (1) volunteers to sign up online, (2) donors to see real-time fundraising progress, (3) beneficiaries to post testimonials. For each feature, specify the new technical components required (client-side, server-side, database) and explain why the old static architecture cannot support it.

STEPS:
- Step 1: Identify the core limitation of Web 1.0: static HTML files cannot accept, store, or reflect user input — every change requires manual file edit and re-upload.
- Step 2: For volunteer sign-up: client-side needs a form (HTML `<form>`) with validation (JS); server-side needs an endpoint (e.g., POST /volunteer) to process data; database needs a `Volunteer` table. Static HTML has no form processing capability.
- Step 3: For real-time fundraising progress: client-side needs periodic AJAX polling or WebSocket to fetch current total; server-side needs an endpoint (GET /api/funds) that queries the database; database needs a `Donation` table with aggregation. Static HTML cannot update without full reload and manual edit.
- Step 4: For beneficiary testimonials: client-side needs a textarea + submit button (form); server-side needs POST /testimonial with moderation queue; database needs `Testimonial` table with status field. Static HTML cannot accept user-generated content at all.
- Step 5: Synthesize: All three features require **server-side logic + persistent storage + asynchronous client-server communication** — the Web 2.0 stack.

REASONING: The migration from Web 1.0 to Web 2.0 is fundamentally about adding **stateful server-side processing** and **bidirectional data flow**. Each feature demands a database write (signup, donation, testimonial) and/or a dynamic read (progress, testimonials list) — impossible with static files alone.

ANSWER: 
- Volunteer sign-up: Form (HTML/JS) → POST /volunteer (Flask/PHP/Node) → INSERT into Volunteer table (MySQL).
- Real-time progress: AJAX GET /api/funds (JS) → SELECT SUM(amount) FROM Donation (SQL) → JSON response → DOM update.
- Testimonials: Form → POST /testimonial → INSERT into Testimonial (status='pending') → Admin moderation interface → Approved testimonials displayed via dynamic template.

## WORKED_EXAMPLE_2
PROBLEM: A student claims "My portfolio website built with React and deployed on Netlify is Web 2.0 because it uses a modern framework." The site has: (a) a contact form that emails the student via a serverless function, (b) a blog section with 10 static Markdown files compiled at build time, (c) a "Dark Mode" toggle saved in localStorage. Evaluate whether this site qualifies as Web 2.0. Justify using three Web 2.0 criteria.

STEPS:
- Step 1: List the three core Web 2.0 criteria: (i) User-generated content / participation, (ii) Dynamic data-driven interactivity (server-side state), (iii) Network effects / social features / API openness.
- Step 2: Analyze feature (a): Contact form → serverless function → email. This is **server-side processing** but only *one-way* (user → owner). No persistent user state, no content visible to others. Partial credit for server interaction.
- Step 3: Analyze feature (b): Blog from static Markdown. Content is **author-generated only**, compiled at build time. No comments, no likes, no user accounts. This is Web 1.0 content delivery, even if built with React.
- Step 4: Analyze feature (c): Dark mode in localStorage. This is **client-side persistence only** — no server involvement, no shared state. It's a UI preference, not Web 2.0 data interaction.
- Step 5: Conclude: The site lacks user accounts, user-generated content visible to others, real-time data, and social/API integration. It is a **static site generated by a modern tool** — architecturally Web 1.0.

REASONING: Web 2.0 is defined by *architecture and user role*, not by the frontend framework. A React site that compiles to static HTML/CSS/JS with no backend API for dynamic data is indistinguishable from a hand-coded static site to the end user. The "serverless function" for email is a microservice, but it doesn't create a platform where users contribute and interact.

ANSWER: The site is **not Web 2.0**. It meets zero of the three core criteria: no user-generated content for public consumption, no server-side dynamic state shared across users, no network effects. It is a **static site (Web 1.0) built with a Web 2.0-era toolchain**.

## WORKED_EXAMPLE_3
PROBLEM: Design a Web 2.0 feature for a **Indian municipal corporation's grievance portal**: citizens can report potholes (with photo + GPS), track status, and upvote others' reports. Officials can assign, update, and close tickets. The system must handle 10,000 concurrent users during monsoon. Specify: (1) Database schema (3+ tables), (2) Key API endpoints (5+), (3) Client-side technologies for photo upload and real-time status, (4) One scalability strategy for the monsoon peak.

STEPS:
- Step 1: Identify core entities: Citizen, Grievance, Official, Vote, StatusUpdate. Map relationships: Citizen 1→M Grievance, Grievance 1→M Vote, Grievance 1→M StatusUpdate, Official 1→M Grievance (assigned).
- Step 2: Design tables: `citizen(id, name, phone, email, password_hash, ward)`, `grievance(id, citizen_id, title, description, photo_url, lat, lng, status, created_at, assigned_official_id)`, `vote(id, grievance_id, citizen_id, created_at)`, `status_update(id, grievance_id, official_id, old_status, new_status, comment, timestamp)`, `official(id, name, dept, password_hash)`.
- Step 3: API endpoints: POST /api/report (multipart: photo + JSON), GET /api/grievances?ward=X&status=open, POST /api/grievances/{id}/vote, PUT /api/grievances/{id}/assign (official), PUT /api/grievances/{id}/status (official), GET /api/grievances/{id}/updates (Server-Sent Events for real-time).
- Step 4: Client-side: React/Vue app; photo upload via `FormData` + `fetch` with progress bar; GPS via `navigator.geolocation`; real-time status via **Server-Sent Events (SSE)** or WebSocket; offline-first with Service Worker for poor connectivity.
- Step 5: Scalability: Use **read replicas** for GET /grievances (heavy read during monsoon), **CDN** for photo storage (S3/Cloudinary), **rate limiting** on POST /report, **asynchronous queue** (Redis + Celery) for photo processing and notifications, **horizontal scaling** of stateless API servers behind load balancer.

REASONING: This problem combines Web 2.0 principles (user-generated geo-tagged content, voting, real-time updates) with **production-grade architectural concerns** (concurrency, media handling, offline support). The schema normalizes relationships; APIs follow REST + SSE for push updates; client uses modern browser APIs; scalability addresses the specific "monsoon peak" load pattern.

ANSWER: 
1. Schema: citizen, grievance, vote, status_update, official (as above).
2. APIs: POST /report, GET /grievances (filtered), POST /grievances/{id}/vote, PUT /grievances/{id}/assign, PUT /grievances/{id}/status, GET /grievances/{id}/updates (SSE).
3. Client: React + FormData + Geolocation API + SSE + Service Worker.
4. Scalability: Read replicas for grievance lists, CDN for photos, async queue for processing, horizontal API scaling.

## COMPETENCY_QUESTION_2
QUESTION: During the 2024 Indian general election, a fact-checking website allows users to submit claims, vote on credibility, and see AI-generated analysis. The site uses: React frontend, Node.js/Express backend, PostgreSQL database, and a Python microservice for AI. During a debate, traffic spikes 100x. The site crashes with "too many connections" on PostgreSQL.  
(a) Identify the **bottleneck** and explain why the architecture failed under spike.  
(b) Propose **two** architectural changes (with specific technologies) to handle such spikes, justifying each with Web 2.0 scalability principles.  
(c) The team wants to add "real-time credibility meter" updating as votes come in. Choose between **polling**, **Server-Sent Events (SSE)**, and **WebSockets** — justify your choice for this use case.

COMPETENCY: System design and scalability analysis / Error identification and correction

STEPS:
- Step 1: (a) Bottleneck: PostgreSQL connection limit exhausted. Each Node.js process opens a connection pool; 100x traffic → 100x concurrent requests → pool exhaustion. Web 2.0's synchronous request/response per vote creates thundering herd.
- Step 2: (b) Change 1: **Connection pooling + read replicas** (PgBouncer + PostgreSQL streaming replication). Offloads read-heavy vote counts to replicas; PgBouncer multiplexes connections. Justification: Web 2.0 read-heavy workloads (leaderboards, feeds) benefit from read scaling.
- Step 3: (b) Change 2: **Async vote ingestion via message queue** (Redis Streams / Kafka + worker consumers). Frontend acknowledges vote instantly; workers batch-write to DB. Justification: Decouples user-facing latency from DB write throughput — core Web 2.0 "eventual consistency" pattern.
- Step 4: (c) Choose **Server-Sent Events (SSE)**. Reason: Unidirectional server→client updates (credibility meter only needs push from server), simpler than WebSockets, works over HTTP/2, auto-reconnects, lower overhead for 100k+ concurrent viewers. Polling wastes bandwidth; WebSockets overkill for one-way data.
- Step 5: Synthesize: The fix transforms synchronous Web 2.0 into **reactive, backpressure-aware** architecture.

ANSWER: 
(a) PostgreSQL connection pool exhaustion due to synchronous per-vote DB writes under 100x spike.  
(b) 1. PgBouncer + read replicas for connection multiplexing and read scaling. 2. Redis Streams + async workers for vote ingestion (write-behind).  
(c) SSE — unidirectional, HTTP-based, efficient for broadcast updates to many clients.
