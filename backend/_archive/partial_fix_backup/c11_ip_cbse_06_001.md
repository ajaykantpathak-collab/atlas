## DEFINITION
File handling is the process of storing data permanently on secondary storage devices (like hard disks) using files, and retrieving or modifying that data through programmatic operations. In Python, files are classified into two fundamental types: **text files** (human-readable, store data as characters with encoding like UTF-8, e.g., .txt, .csv, .py) and **binary files** (store raw bytes, not directly human-readable, e.g., .jpg, .exe, .dat, pickle files).

## WALKTHROUGH
Imagine you wrote a Python program to manage student marks for your Class 11 practical exam. You enter 50 students' names and marks, but when you close the program and open it tomorrow — all data is gone! This happens because variables live only in RAM (temporary memory). To save data permanently, we need **files** on the hard disk. Think of a file like a notebook: you open it, write/read, then close it. In Python, we have two kinds of notebooks: **text files** (like a diary you can read directly — .txt, .csv) and **binary files** (like a sealed envelope with encoded content — images, compiled programs). The key insight: every file operation follows the same three-step rhythm — open → do work → close — whether you're saving a shopping list or a school database.

## DIAGNOSTIC_QUESTION_1
What is the fundamental difference between a text file and a binary file in terms of how data is stored and read by humans?

## DIAGNOSTIC_ANSWER_1
A text file stores data as encoded characters (e.g., UTF-8) that humans can read directly when opened in a text editor (like Notepad), while a binary file stores raw bytes that appear as unreadable symbols in a text editor and require specific software to interpret. A wrong answer (e.g., "text files are smaller" or "binary files are only for images") reveals the student confuses file *type* with file *size* or *extension*, not understanding that the distinction is about **data representation** (characters vs raw bytes).

## DIAGNOSTIC_QUESTION_2
A student writes a Python program that stores a list of 100 integers in a variable `marks = [95, 87, 78, ...]`. They run the program, then close it. Next day they run the program again and expect `marks` to still have the data. Why does this fail, and how does a file solve it?

## DIAGNOSTIC_ANSWER_2
Variables like `marks` reside in RAM (volatile memory), which is cleared when the program terminates or the computer shuts down. Files reside on secondary storage (hard disk/SSD), which is non-volatile — data persists without power. A wrong answer (e.g., "Python doesn't save variables automatically" without mentioning RAM vs disk) shows the student doesn't grasp the **hardware-level reason** for persistence failure, which is essential to appreciate *why* file handling exists.

## DIAGNOSTIC_QUESTION_4
Compare and contrast: Why can you open a `.py` Python script in Notepad and read it, but opening a `.exe` compiled program in Notepad shows garbage characters? Relate this to the text vs binary file distinction.

## DIAGNOSTIC_ANSWER_4
A `.py` file is a **text file** — it contains source code written as human-readable characters encoded in UTF-8/ASCII. A `.exe` is a **binary file** — it contains machine code (raw bytes: instructions, addresses, metadata) meant for the CPU, not humans. Notepad tries to decode bytes as text; for `.exe`, those byte values don't map to valid characters, showing garbage. A wrong answer (e.g., ".exe is encrypted" or ".py is smaller") shows the student confuses **encoding purpose** (human vs machine) with encryption or size.

## DIAGNOSTIC_QUESTION_5
A student argues: "Since binary files can store *any* data (text, images, numbers), we should always use binary mode (`'wb'`, `'rb'`) in Python and never text mode." Evaluate this claim. Is it correct? Justify your answer with two specific drawbacks of using binary mode for text data.

## DIAGNOSTIC_ANSWER_5
The claim is **incorrect**. While binary mode *can* store text (by encoding strings to bytes manually), it introduces two major drawbacks: (1) **No automatic newline handling** — text mode translates `\n` to `\r\n` on Windows automatically; binary mode requires manual management, causing cross-platform bugs. (2) **No encoding abstraction** — text mode handles UTF-8/ASCII encoding/decoding transparently; binary mode forces you to `.encode()`/`.decode()` every string, increasing errors. A wrong evaluation (e.g., "binary is faster so always use it") shows the student ignores **developer productivity and portability** trade-offs.

## DIAGNOSTIC_QUESTION_6
Design a real-world scenario (Indian context) where a school management system must use **both** text and binary files together. Describe what data goes in each, and explain why mixing them in a single file type would be problematic.

## DIAGNOSTIC_ANSWER_6
**Scenario:** A CBSE school stores student records in `students.csv` (text) — Name, Roll No, Class, Marks — and student photographs in `photos/` folder as `.jpg` files (binary), referenced by Roll No in the CSV.

## COMMON_MISCONCEPTION
Students often believe that **"file handling is only about reading/writing `.txt` files"** because early examples use text files. They think binary files are "advanced" or "only for images." This leads to errors like trying to write an image using `file.write("binary_data")` in text mode (corrupting data), or opening a `.dat` pickle file in `'r'` mode (causing `UnicodeDecodeError`). The root cause: they don't realize **every file is bytes on disk** — text mode is just a *convenience layer* that auto-encodes/decodes and handles newlines. Binary mode gives raw access; text mode gives interpreted access. Neither is "more powerful" — they serve different data natures.

## WORKED_EXAMPLE_1
PROBLEM: A school library wants to digitize its catalog. Each book record has: Book ID (integer), Title (string), Author (string), Year (integer), and a scanned cover image (JPG). The librarian needs to: (a) search books by title/author quickly, (b) display cover images in a GUI, (c) export the catalog to Excel for the principal. Decide which data goes in a text file and which in binary files, and justify.

STEPS:
- Step 1: Identify data types — Book ID, Title, Author, Year are structured textual/numeric data; cover image is unstructured binary data.
- Step 2: Match to file types — Structured data → text file (CSV); images → binary files (JPG).
- Step 3: Justify for search/export — CSV can be read by Python's `csv` module, pandas, and Excel directly; searching/filtering is easy.
- Step 4: Justify for images — JPG is already a binary format; storing as binary preserves exact bytes for GUI display without re-encoding overhead.
- Step 5: Design the linkage — Store CSV with columns: Book_ID, Title, Author, Year, Cover_Filename; save each cover as `cover_<Book_ID>.jpg` in a folder.
REASONING: Text files (CSV) excel at structured, human-readable, tool-compatible data. Binary files excel at preserving exact byte sequences for non-text media. Separating them leverages each format's strength.
ANSWER: Book metadata → `catalog.csv` (text); Cover images → `covers/cover_<Book_ID>.jpg` (binary). Link via Book_ID in CSV.

## WORKED_EXAMPLE_2
PROBLEM: A student writes a Python program to save the high score of a game. They use `open('highscore.txt', 'w')` and write the integer `9850` directly. Next day, they read the file and get the string `'9850'`. They try `score + 100` and get a TypeError. Explain why this happens and how to fix it using text file concepts.

STEPS:
- Step 1: Recognize that `open(..., 'w')` opens in **text mode** — Python expects strings, not integers.
- Step 2: When writing, Python implicitly converts `9850` to string `'9850'` (via `str()`) and encodes to bytes (UTF-8) for disk.
- Step 3: When reading in text mode (`'r'`), Python decodes bytes to string `'9850'` — not an integer.
- Step 4: The TypeError occurs because `'9850' + 100` tries to concatenate string and int.
- Step 5: Fix: Convert explicitly on read: `score = int(file.read())` or on write: `file.write(str(score))` — but reading still returns string, so `int()` is mandatory.
REASONING: Text mode *always* returns strings on read. The programmer must handle type conversion (int/float) explicitly — Python does not preserve Python types in text files.
ANSWER: Text files store only character sequences. Reading returns `str`. Fix: `score = int(open('highscore.txt').read())`.

## WORKED_EXAMPLE_3
PROBLEM: A Class 11 project stores student records in a binary file `students.dat` using `pickle.dump()`. The teacher asks: "Can I open this in Notepad to check the data?" The student says yes. Is the student correct? If not, explain what the teacher would see and why. Then propose a better file format for teacher readability while keeping Python-loadable structure.

STEPS:
- Step 1: Identify that `pickle` writes **binary** data (serialized Python objects) — not text.
- Step 2: Notepad tries to decode file bytes as UTF-8 text. Pickle bytes include control bytes, length prefixes, object headers — most are non-printable.
- Step 3: Teacher would see: garbage characters (�, □, ♥), maybe fragments of strings like "RollNo" or "Name", but no readable table.
- Step 4: Why? Binary ≠ text. Pickle prioritizes Python object fidelity (lists, dicts, classes) over human readability.
- Step 5: Better format: **CSV (text)** for tabular data — teacher opens in Excel/Notepad; Python reads with `csv` module. Or **JSON (text)** for nested data — readable + Python-loadable.
REASONING: Binary formats (pickle, .npy, .dat) are for *program-to-program* transfer. Text formats (CSV, JSON, XML) are for *human-program* interchange. The teacher is human → needs text.
ANSWER: Student is wrong. Teacher sees corrupted garbage. Use `students.csv` (text) for readability + Python compatibility.

## COMPETENCY_QUESTION_2
QUESTION: A student writes this code to save a list of temperatures (in °C) recorded over a week:
```python
temps = [32.5, 33.0, 31.8, 34.2, 33.5, 32.0, 31.5]
f = open('week_temps.txt', 'wb')  # binary mode
for t in temps:
    f.write(t)
f.close()
```
The code crashes with `TypeError: a bytes-like object is required, not 'float'`.  
(a) Explain *why* this error occurs, referencing the difference between text and binary mode.  
(b) Fix the code in **two different ways**: one using text mode, one staying in binary mode.  
(c) Which fix is better for this scenario? Justify.

COMPETENCY: Error identification and correction with mode-appropriate serialization

STEPS:
- Step 1: Binary mode `write()` expects `bytes`, not `float`. `t` is a Python float → must be converted to bytes.
- Step 2: Fix 1 (text mode): Change `'wb'` → `'w'`, use `f.write(str(t) + '\n')`. Text mode auto-encodes string to bytes.
- Step 3: Fix 2 (binary mode): Keep `'wb'`, use `f.write(struct.pack('f', t))` or `f.write(str(t).encode() + b'\n')`. Manual encoding required.
- Step 4: Compare — Text mode is simpler, human-readable, cross-platform. Binary mode with `struct` is compact but needs `struct.unpack` to read; with `str().encode()` it's verbose.
- Step 5: Choose text mode — temperatures are numeric text data; no need for binary precision/compactness.
ANSWER: (a) Binary mode requires bytes; float is not bytes. (b) Text: `open('week_temps.txt', 'w')` + `f.write(f'{t}\n')`. Binary: `open('week_temps.txt', 'wb')` + `f.write(struct.pack('f', t))`. (c) Text mode better — human-readable, editable, no struct dependency, newline-safe.
