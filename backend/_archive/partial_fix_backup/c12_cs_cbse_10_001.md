## DEFINITION
File handling is the process of storing data persistently on secondary storage (hard disk, SSD) using named files, allowing programs to read from and write to these files across multiple executions. In Python, files are categorised as text files (human-readable, store data as characters with encoding like UTF-8) and binary files (store raw bytes, used for images, audio, executables, pickled objects).

## WALKTHROUGH
Imagine you built a student mark tracker in Python that runs perfectly — but every time you close the program, all entered marks vanish. How would you save the data so it survives a restart? That is the problem file handling solves. Start by asking: "Where does data live when the program isn't running?" Guide students to realise RAM is volatile; secondary storage (files) is non-volatile. Introduce the analogy of a notebook (file) vs whiteboard (RAM). Then classify files: open a .txt file in Notepad (readable text) vs an .exe or .jpg in Notepad (garbage characters) to show text vs binary difference. Conclude with the three-step mental model: open → read/write → close.

## DIAGNOSTIC_QUESTION_1
What is the fundamental difference between a text file and a binary file in terms of how data is stored and interpreted by Python?

## DIAGNOSTIC_ANSWER_1
A text file stores data as encoded characters (e.g., UTF-8, ASCII) where each byte or byte-sequence represents a human-readable character; Python automatically handles encoding/decoding when opening in text mode. A binary file stores raw bytes without any character encoding; Python returns bytes objects and performs no translation. A wrong answer (e.g., "text files are .txt and binary files are .dat") reveals the student confuses file extension with storage format — the same file can be opened in either mode, but interpretation differs.

## DIAGNOSTIC_QUESTION_2
A student writes a Python program that opens a file in 'w' mode, writes "Hello", closes it, then reopens the same file in 'r' mode and reads it. They claim the file now contains "HelloHello" because 'w' appends. Is the student correct? Explain why or why not.

## DIAGNOSTIC_ANSWER_2
The student is incorrect. Opening a file in 'w' (write) mode truncates the file to zero length before writing — it does NOT append. The file will contain only "Hello". If the student thought 'w' appends, they are confusing 'w' with 'a' (append) mode. This misconception is extremely common and causes data loss in board practicals when students intend to add records but overwrite the entire file instead.

## DIAGNOSTIC_QUESTION_3
You have a CSV file "marks.csv" containing student names and marks (text data). You also have a compiled Python module "mymodule.pyc" (bytecode). Which file should be opened in text mode ('r') and which in binary mode ('rb')? Justify your choice for each.

## DIAGNOSTIC_ANSWER_3
"marks.csv" should be opened in text mode ('r') because it contains human-readable character data (comma-separated values) that Python should decode using the default encoding (UTF-8) into str objects for easy processing (split, strip, int conversion). "mymodule.pyc" must be opened in binary mode ('rb') because it contains raw bytecode — non-text bytes that have no valid character encoding; opening in text mode would raise UnicodeDecodeError or produce corrupted data. A wrong assignment shows the student cannot match file content type to the correct mode.

## DIAGNOSTIC_QUESTION_4
Compare the following two scenarios: (A) A program writes a list of integers [10, 20, 30] to a file using text mode with str() conversion. (B) The same list is written using pickle.dump() in binary mode. Analyse the differences in (i) file size, (ii) human readability, (iii) ease of reading back into a Python list, and (iv) cross-language portability.

## DIAGNOSTIC_ANSWER_4
(A) Text mode: larger file size (characters "10, 20, 30" plus delimiters), human-readable in any editor, requires manual parsing (split, int) to reconstruct list, portable to any language (CSV-like). (B) Binary pickle: smaller (compact binary representation), not human-readable (garbage in text editor), trivial to read back with pickle.load() directly into list, Python-specific (not portable). A student who says "both are same" misses the core trade-off: text for interoperability, binary for Python-specific efficiency and fidelity.

## DIAGNOSTIC_QUESTION_5
Evaluate this statement: "Since binary files are more compact and faster, we should always use binary mode for all file operations in Python." Defend or refute with at least three concrete arguments.

## DIAGNOSTIC_ANSWER_5
Refute. Arguments: (1) Human readability & debugging: text files (logs, config, CSV) can be inspected/edited with Notepad, vi, Excel — critical for maintenance. (2) Interoperability: text (JSON, CSV, XML) is language-agnostic; pickle is Python-only. (3) Encoding control: text mode lets you specify encoding (utf-8, utf-16) for internationalisation; binary mode gives raw bytes — you must handle encoding manually. (4) Simplicity: for simple data (marks, names), text mode with split() is easier than struct/pickle. A student who agrees ignores real-world software engineering constraints.

## DIAGNOSTIC_QUESTION_6
Design a real-world scenario (Indian context) where choosing the wrong file mode (text vs binary) would cause a silent data corruption bug that is hard to detect. Describe the scenario, the wrong mode used, the symptom, and why it is silent.

## DIAGNOSTIC_ANSWER_6
Scenario: A banking app stores transaction records (date, amount, account) using Python's pickle in binary mode. A developer later decides to "view" the file and opens it in text mode ('r') to print contents, then accidentally saves it (e.g., via an editor auto-save). The pickle byte stream gets corrupted by UTF-8 decoding/re-encoding (invalid bytes replaced, newline translation on Windows). Symptom: Next run, pickle.load() raises EOFError or unpicklingError — but only for that file; other files work. Silent because: no error at save time, corruption detected only on next read, and the developer may blame "pickle bug" not their text-mode edit. Correct answer must identify newline translation (CRLF↔LF) and encoding replacement as the silent corruption mechanisms.

## COMMON_MISCONCEPTION
Students believe file extension determines file type: ".txt means text file, .dat/.bin means binary file". They think opening a .dat file in text mode will "convert it to text" or that a .txt file opened in binary mode "becomes binary". In reality, file type is defined by CONTENT and HOW YOU OPEN IT — the same file "data.txt" opened as 'r' yields str (decoded), opened as 'rb' yields bytes (raw). This misconception leads to UnicodeDecodeError when reading binary files as text, or corrupted output when writing text files as binary without encoding.

## WORKED_EXAMPLE_1
PROBLEM: A school stores student attendance in a text file "attendance.txt" where each line is "RollNo,Name,Present/Absent". The file currently has 500 lines. The admin wants to know: (a) approximate file size in bytes, (b) whether this file can be opened in Microsoft Excel directly, (c) what happens if they accidentally open it in binary mode ('rb') and print the first line.

STEPS:
- Step 1: Estimate average line length — "101,Anita Sharma,P" ≈ 20 characters + 1 newline = 21 bytes per line (UTF-8, ASCII chars).
- Step 2: Calculate total size — 500 lines × 21 bytes ≈ 10,500 bytes ≈ 10.5 KB.
- Step 3: Determine Excel compatibility — CSV-like format with comma delimiter; Excel can open .txt files via Data → From Text/CSV, so YES.
- Step 4: Predict binary mode behaviour — open('attendance.txt','rb').readline() returns bytes object b'101,Anita Sharma,P\n'; printing shows b'101,Anita Sharma,P\\n' with b-prefix and escaped newline.
- Step 5: Verify — text mode would decode to str '101,Anita Sharma,P\n'; binary mode gives raw bytes, no decoding.

REASONING: Text files store encoded characters; size ≈ character count × bytes-per-char (1 for ASCII, up to 4 for UTF-8). Binary mode bypasses decoding, returning bytes. CSV-like text files are spreadsheet-compatible.

ANSWER: (a) ~10.5 KB, (b) Yes (comma-delimited text), (c) Prints b'101,Anita Sharma,P\\n' (bytes object with literal backslash-n).

## WORKED_EXAMPLE_2
PROBLEM: A Python script saves a dictionary of product prices {"apple": 120, "banana": 40, "mango": 80} using two methods: Method A — write as JSON text file; Method B — write as pickle binary file. The dictionary is later read back. Compare the two methods on: (i) file content appearance, (ii) Python code to read back, (iii) ability to edit prices manually in Notepad.

STEPS:
- Step 1: Method A (JSON text) — json.dump(dict, file) writes human-readable text: {"apple": 120, "banana": 40, "mango": 80}. File size ≈ 50 bytes.
- Step 2: Method B (pickle binary) — pickle.dump(dict, file) writes binary serialization: bytes like b'\x80\x04\x95...\x94}' — unreadable in text editor.
- Step 3: Reading back Method A — json.load(file) returns dict directly; requires import json.
- Step 4: Reading back Method B — pickle.load(file) returns dict directly; requires import pickle.
- Step 5: Manual edit — Method A file can be opened in Notepad, change "120" to "130", save; Method B file cannot be meaningfully edited — any change corrupts pickle stream.

REASONING: JSON is text-based, language-independent, editable; pickle is Python-specific binary, compact, preserves exact Python objects (including custom classes), but opaque and fragile to manual edits.

ANSWER: (i) JSON: readable text; pickle: binary garbage. (ii) Both one-liners (json.load vs pickle.load). (iii) JSON: yes; pickle: no (corruption).

## WORKED_EXAMPLE_3
PROBLEM: A CBSE Class 12 practical exam question asks: "Write a Python program to create a binary file 'students.dat' storing records of 5 students. Each record has roll number (int), name (str), and marks (float). Use the struct module to pack each record into fixed-size binary format." Explain why struct is preferred over pickle here, and calculate the file size if each record uses format 'i20sf' (int, 20-char string, float).

STEPS:
- Step 1: Identify struct format 'i20sf' — i = 4 bytes (int), 20s = 20 bytes (fixed-length string, padded/truncated), f = 4 bytes (float). Total per record = 28 bytes.
- Step 2: Calculate total file size — 5 records × 28 bytes = 140 bytes exactly (no overhead).
- Step 3: Explain struct vs pickle — struct gives fixed-length, C-compatible, predictable layout; essential for random access (seek to record n) and interoperability with C/C++ programs. Pickle is variable-length, Python-only, includes type metadata — unsuitable for fixed-record binary files.
- Step 4: Note padding — name "Rahul" (5 chars) becomes 20 bytes with 15 null bytes (\x00) padding; ensures every record same size.
- Step 5: Verify exam relevance — CBSE practical often tests struct for binary file record handling; pickle is taught separately (c12_cs_cbse_10_011).

REASONING: struct.pack/unpack provides deterministic binary layout — critical for random access (seek) and competitive exam questions on file indexing. Pickle is for object serialization, not fixed-record databases.

ANSWER: File size = 140 bytes. struct preferred for fixed-record size, random access, and C-compatibility; pickle for arbitrary Python object graphs.

## COMPETENCY_QUESTION_1
QUESTION: A teacher maintains a text file "marks.txt" with lines like "101|Amit|85|90|78" (roll|name|marks1|marks2|marks3). She wants to compute each student's average and write results to "averages.txt" as "101|Amit|84.33". She writes code that opens "marks.txt" in 'r' mode, reads all lines, splits by '|', computes average, and writes to "averages.txt" opened in 'w' mode. Identify TWO potential bugs in this approach related to file modes and data handling, and suggest fixes.

COMPETENCY: Error identification and correction in file handling logic
STEPS:
- Step 1: Identify that 'w' mode on output file truncates it each time — but since she opens it once before loop, this is OK. Wait — if she opens inside the loop, it truncates repeatedly. Bug 1: Opening output file inside the loop in 'w' mode loses previous lines. Fix: Open once before loop, or use 'a' mode.
- Step 2: Identify that input file may have trailing newline — split('|') on "101|Amit|85|90|78\n" gives last element "78\n". int("78\n") works but float("78\n") works; however, strip() is safer. Bug 2: Not stripping newline before split causes marks3 to have trailing newline. Fix: line.strip().split('|').
- Step 3: Consider encoding — if names have non-ASCII (e.g., "आमिर"), default encoding may fail on some systems. Fix: open(..., encoding='utf-8').
- Step 4: Final check — both bugs are silent (wrong output, no crash), typical of board practical errors.

ANSWER: Bug 1: Opening output file in 'w' mode inside the loop truncates previous content — only last student's average remains. Fix: Open output file once before loop, or use 'a' (append) mode. Bug 2: Not stripping newline before split causes last mark to include '\n' (e.g., "78\n"), which int() handles but is fragile. Fix: Use line.strip().split('|'). Additional: Specify encoding='utf-8' for non-ASCII names.
DIFFICULTY: medium

Evaluate each option against all four requirements and recommend the best choice with justification.
