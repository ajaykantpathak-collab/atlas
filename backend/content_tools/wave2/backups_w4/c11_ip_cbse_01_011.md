## ELI5
A temperature sensor hands your microcontroller 8-bit binary like 10110110, but the display library wants hexadecimal - and there is a two-second trick. Because 16 is 2 to the 4th, every hex digit is exactly 4 bits: split 10110110 into 1011 and 0110, read them as 11 and 6, write B6. Going the other way, decimal-to-binary is repeated division by 2 - divide, record the remainder, repeat with the quotient, then read the remainders bottom-up. Every conversion is positional weights or a shortcut through binary, and a reverse conversion checks the answer.

## DEFINITION
Conversion between number systems is the process of representing a given numeric value in a different base (radix) using positional notation, where each digit's weight is a power of the base. For bases 2 (binary), 8 (octal), 10 (decimal), and 16 (hexadecimal), conversion relies on the mathematical equivalence: \( N = \sum_{i} d_i \times b^i \), where \( d_i \) is the digit at position \( i \) (0-indexed from right) and \( b \) is the base.

## WALKTHROUGH
Imagine you are programming a microcontroller that reads a temperature sensor giving 8-bit binary output (e.g., `10110110`), but your display library only accepts hexadecimal strings. How do you translate `10110110` to hex without a calculator? Start by recalling that each hex digit represents exactly 4 binary bits. Split the 8-bit string into two groups of 4: `1011` and `0110`. Convert each group to its decimal equivalent (11 and 6), then map to hex digits (B and 6), giving `B6`. This grouping trick works because \( 16 = 2^4 \). For decimal-to-binary, use repeated division by 2: write the number, divide by 2, record remainder, repeat with quotient until 0, then read remainders bottom-up. The key insight is that every conversion is either a direct base-change using positional weights or a shortcut via binary because 8 and 16 are powers of 2.

Takeaway: mastery means choosing the right route - positional-weight expansion for any base change, repeated division for decimal-to-binary, 3-bit grouping for binary-octal and 4-bit grouping for binary-hex - and verifying by converting back. Exam moves: convert-and-verify questions and pick-the-method items on the sensor scene. Check yourself: grouping works only because 8 and 16 are powers of 2; decimal plays no such shortcut. Students miss it because four methods sound like four topics, when the shared positional formula shows the design: every digit is a digit times base to the position, and the shortcuts are just that formula pre-computed for friendly group sizes.

## DIAGNOSTIC_QUESTION_1
What is the hexadecimal equivalent of the binary number `11010110`? Show the grouping steps.

## DIAGNOSTIC_ANSWER_1
Correct answer: `D6`. Group `11010110` into `1101` (13 → D) and `0110` (6 → 6). A wrong answer like `1D6` reveals the student grouped from the left instead of the right (LSB), or forgot to pad with leading zeros for incomplete groups. This indicates a misunderstanding of positional grouping alignment.

## DIAGNOSTIC_QUESTION_2
Explain why the repeated-division-by-2 method for decimal-to-binary conversion produces the correct binary digits in reverse order (LSB first).

## DIAGNOSTIC_ANSWER_2
Correct explanation: Each division by 2 yields a remainder of 0 or 1, which is exactly the coefficient of \( 2^0 \) in the current quotient's representation. The quotient then represents the remaining higher powers. Reading remainders bottom-up reconstructs the number from MSB to LSB. A wrong answer that says "it's just a rule" or "we divide by 2 because binary is base 2" without linking to positional weights shows procedural memorisation without conceptual understanding of the division algorithm's connection to polynomial expansion.

## DIAGNOSTIC_QUESTION_3
Convert the decimal number 45.6875 to binary. Show all steps for both integer and fractional parts.

## DIAGNOSTIC_ANSWER_3
Integer part (45): 45÷2=22 r1, 22÷2=11 r0, 11÷2=5 r1, 5÷2=2 r1, 2÷2=1 r0, 1÷2=0 r1 → `101101`. Fractional part (0.6875): 0.6875×2=1.375 →1, 0.375×2=0.75 →0, 0.75×2=1.5 →1, 0.5×2=1.0 →1 → `.1011`. Combined: `101101.1011`. A wrong answer that stops fractional multiplication early (e.g., `.101`) or misorders integer remainders (e.g., `101101` read top-down) reveals confusion between the two algorithms' directionality.

## DIAGNOSTIC_QUESTION_4
A student converts octal `73.4` to binary by writing each octal digit as a 3-bit group: `111 011 . 100` → `111011.100`. Another student converts the same octal number to decimal first (7×8+3=59, 4/8=0.5 → 59.5) then to binary (`111011.1`). Are both results equivalent? Justify.

## DIAGNOSTIC_ANSWER_4
Yes, both are equivalent: `111011.100` = `111011.1` because trailing zeros after the binary point do not change the value. The first method (direct grouping) is faster and exact; the second (via decimal) risks rounding errors for non-terminating fractions. A student who says "they are different because one has three fractional bits and the other has one" fails to recognise that `0.100₂ = 0.1₂ = 0.5₁₀`, indicating a gap in understanding fractional positional equivalence across bases.

## DIAGNOSTIC_QUESTION_5
Critique the following conversion: "To convert hexadecimal `2F` to octal, I convert each hex digit to 3 binary bits: `2`→`010`, `F`→`111`, giving `010111`, then group into 3-bit octal groups: `010 111` → `27` octal." Is this method valid? Why or why not?

## DIAGNOSTIC_ANSWER_5
The method is invalid because hexadecimal digits require 4 binary bits each (since \( 16 = 2^4 \)), not 3. The correct binary for `2F` is `0010 1111`. Grouping `00101111` into 3-bit groups from right: `00 101 111` → pad left group → `000 101 111` → octal `057` or `57`. The student's error stems from confusing the grouping size for octal (3 bits) with the expansion size for hex (4 bits). This reveals a misconception that all base conversions use the same group size.

## DIAGNOSTIC_QUESTION_6
Design a step-by-step algorithm (in plain English) that converts any positive decimal integer to hexadecimal directly without using binary as an intermediate. Then apply it to convert 1000₁₀ to hex.

## DIAGNOSTIC_ANSWER_6
Algorithm: (1) Divide the decimal number by 16. (2) Record the remainder (0-15, using 0-9, A-F). (3) Replace the number with the quotient. (4) Repeat until quotient is 0. (5) Read remainders from last to first. Application: 1000÷16=62 r8, 62÷16=3 r14(E), 3÷16=0 r3 → `3E8`. A poor answer that uses binary intermediate or misorders remainders shows inability to generalise the division algorithm to arbitrary bases.

## COMMON_MISCONCEPTION
Students often treat the binary point (radix point) differently from the decimal point, believing that fractional conversion "stops" when the fractional part becomes zero in decimal, not realising that many decimal fractions (e.g., 0.1) are non-terminating in binary. They also frequently misalign grouping for binary↔octal/hex by starting groups from the left (MSB) instead of the right (LSB), leading to incorrect padding. For example, converting binary `10110` to octal: wrong grouping `10 110` → `26`; correct grouping from right `010 110` → `26` (same here by coincidence) but for `11010` wrong `11 010` → `32`, correct `011 010` → `32` (again coincidence) – the error becomes obvious with `101` → wrong `1 01` → `11` (3), correct `101` → `5`.

## WORKED_EXAMPLE_1
PROBLEM: Convert the decimal number 156.3125 to binary, octal, and hexadecimal. Show all steps.
STEPS:
- Step 1: Separate integer part (156) and fractional part (0.3125).
- Step 2: Convert integer 156 to binary using repeated division by 2: 156÷2=78 r0, 78÷2=39 r0, 39÷2=19 r1, 19÷2=9 r1, 9÷2=4 r1, 4÷2=2 r0, 2÷2=1 r0, 1÷2=0 r1. Read remainders bottom-up: 10011100₂.
- Step 3: Convert fractional 0.3125 to binary using repeated multiplication by 2: 0.3125×2=0.625 →0, 0.625×2=1.25 →1, 0.25×2=0.5 →0, 0.5×2=1.0 →1. Read top-down: .0101₂.
- Step 4: Combine: 156.3125₁₀ = 10011100.0101₂.
- Step 5: Convert binary to octal by grouping 3 bits from binary point outward: integer 010 011 100 → 2 3 4, fractional 010 100 → 2 4. Result: 234.24₈.
- Step 6: Convert binary to hexadecimal by grouping 4 bits: integer 1001 1100 → 9 C, fractional 0101 → 5. Result: 9C.5₁₆.
- Step 7: Verify by converting octal 234.24₈ back to decimal: 2×8²+3×8+4 + 2/8+4/64 = 128+24+4+0.25+0.0625 = 156.3125. Correct.
REASONING: The division algorithm extracts LSB first because each division by 2 isolates the 2⁰ coefficient. Multiplication by 2 shifts the fractional part left, exposing the 2⁻¹ coefficient as the integer part of the product. Grouping works because 8=2³ and 16=2⁴, so each octal/hex digit exactly corresponds to 3/4 binary bits.
ANSWER: Binary: 10011100.0101₂, Octal: 234.24₈, Hexadecimal: 9C.5₁₆

## WORKED_EXAMPLE_2
PROBLEM: Convert hexadecimal 3F.8 to decimal, binary, and octal.
STEPS:
- Step 1: Hex to decimal: 3×16¹ + F×16⁰ + 8×16⁻¹ = 3×16 + 15×1 + 8/16 = 48 + 15 + 0.5 = 63.5₁₀.
- Step 2: Hex to binary: Expand each hex digit to 4 bits: 3 → 0011, F → 1111, 8 → 1000. Result: 00111111.1000₂ (or 111111.1₂ after dropping leading/trailing zeros).
- Step 3: Binary to octal: Group binary 111111.1 into 3-bit groups from binary point: integer 111 111 → 7 7, fractional 100 → 4. Result: 77.4₈.
- Step 4: Verify octal to decimal: 7×8¹ + 7×8⁰ + 4×8⁻¹ = 56 + 7 + 0.5 = 63.5₁₀. Matches.
- Step 5: Alternative direct hex to octal via binary is the standard method; no direct hex↔octal digit mapping exists because 16 and 8 are not powers of each other.
REASONING: Hexadecimal is base 16 (2⁴), so each digit maps to exactly 4 binary bits. Octal is base 8 (2³), so each digit maps to 3 binary bits. Binary serves as the universal intermediate because both 8 and 16 are powers of 2. The fractional hex digit 8 (8/16 = 1/2) becomes binary .1 and octal .4 (4/8 = 1/2).
ANSWER: Decimal: 63.5, Binary: 111111.1₂, Octal: 77.4₈

## WORKED_EXAMPLE_3
PROBLEM: A microcontroller register holds the 16-bit binary value `1010 0011 1100 1101`. The datasheet says bits 15-12 represent a 4-bit configuration code (hex), bits 11-8 represent an 8-bit sensor ID (hex), and bits 7-0 represent a signed 8-bit temperature offset (two's complement, but here treat as unsigned hex). Extract each field in hexadecimal.
STEPS:
- Step 1: Write the 16-bit binary with spaces every 4 bits for hex: `1010 0011 1100 1101`.
- Step 2: Identify bit positions: bit 15 is leftmost (MSB), bit 0 is rightmost (LSB).
- Step 3: Extract bits 15-12 (first 4 bits): `1010` → A₁₆. This is the configuration code.
- Step 4: Extract bits 11-8 (next 4 bits): `0011` → 3₁₆. This is the sensor ID.
- Step 5: Extract bits 7-0 (last 8 bits): `1100 1101` → C D₁₆. This is the temperature offset byte.
- Step 6: Verify by reconstructing: A 3 C D → `1010 0011 1100 1101`. Matches original.
- Step 7: If the temperature offset were to be interpreted as signed two's complement, `CD`₁₆ = `1100 1101`₂ → MSB=1 indicates negative; magnitude = invert+1 = `0011 0011`₂ = 33H = 51₁₀, so -51. But the problem asks for unsigned hex extraction only.
REASONING: This example combines conversion with bit-field extraction, a common task in embedded programming. Hexadecimal is used because each hex digit aligns with 4-bit boundaries, making register maps readable. The conversion is essentially binary-to-hex grouping, but the context requires understanding bit numbering (0=LSB) and field boundaries.
ANSWER: Configuration code: A₁₆, Sensor ID: 3₁₆, Temperature offset: CD₁₆

## COMPETENCY_QUESTION_1

COMPETENCY: Error identification and correction

- Step 4: Group binary into 4-bit groups from binary point: integer 1 0111 1010 → pad to 0001 0111 1010 → 1 7 A, fractional 1000 → 8. Result: 17A.8₁₆.
