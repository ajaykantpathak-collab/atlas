## ELI5
Type an address, press Enter — before the page appears, a global phonebook translates the name into a number. The Domain Name System (DNS) is a hierarchical, decentralized naming system translating human-readable domain names into numerical IP addresses needed to locate services and devices; a URL is the structured string specifying a web resource — scheme, host, port, path, query, fragment. The lookup walks the hierarchy: browser cache, OS cache, recursive resolver, root, TLD, authoritative — no single server knows every name, and that is the point.

## DEFINITION
The Domain Name System (DNS) is a hierarchical, decentralized naming system that translates human-readable domain names (e.g., www.example.com) into numerical IP addresses (e.g., 192.0.2.1) required for locating and identifying computer services and devices on a network. A Uniform Resource Locator (URL) is a structured string that specifies the address of a resource on the web, comprising components such as scheme, host, port, path, query, and fragment.

## WALKTHROUGH
Imagine you type "https://www.cbse.gov.in/exam/schedule.pdf" in your browser and press Enter. Before any webpage appears, your computer must find the IP address of "www.cbse.gov.in". How does it know which server to contact? We start by asking: what happens between pressing Enter and seeing the page? The answer lies in DNS — a global, distributed phonebook. We first break the URL into its parts (scheme=https, host=www.cbse.gov.in, path=/exam/schedule.pdf). Then we follow the DNS lookup: your browser checks its cache, then the OS cache, then your ISP's recursive resolver, which walks the hierarchy from root servers to .in TLD servers to cbse.gov.in authoritative servers. Each step either answers directly or refers to the next level. The key insight is that DNS trades a centrally managed directory for a scalable, fault-tolerant hierarchy where no single server knows all mappings.

Takeaway: mastery means the URL split into six parts and the resolution traced resolver by resolver. Exam moves: tracing questions follow the DNS process distinguishing recursive from iterative queries; decomposition questions break a URL into scheme, host, port, path, query and fragment with each purpose stated. Method: take the typed address, slice it — scheme, host, path — then follow the miss upward: caches, resolver, root, TLD, authoritative, answer cached for next time. Drill: six components, five lookup steps, one recursive-iterative distinction. Students miss it because "the internet knows" hides the whole hierarchy.

## DIAGNOSTIC_QUESTION_1
What does DNS stand for, and what is its primary function in computer networks?

## DIAGNOSTIC_ANSWER_1
DNS stands for Domain Name System. Its primary function is to translate human-readable domain names (like www.example.com) into machine-readable IP addresses (like 192.0.2.1) so that devices can locate each other on a network. A wrong answer (e.g., "DNS assigns IP addresses" or "DNS routes packets") reveals the student confuses name resolution with address allocation (DHCP) or packet forwarding (routing).

## DIAGNOSTIC_QUESTION_2
Explain why the DNS namespace is organized as a hierarchy (root → top-level domains → second-level domains → subdomains) rather than as a flat list of all domain-to-IP mappings.

## DIAGNOSTIC_ANSWER_2
A hierarchical namespace allows decentralized administration: each zone (e.g., .com, .in, example.com) is managed independently, enabling scalability to billions of names and fault isolation (a failure in .in does not affect .com). A flat list would require a single central database, creating a bottleneck, single point of failure, and impossible administrative coordination. If a student says "hierarchy makes lookups faster" without mentioning delegation and autonomy, they miss the core design principle of distributed authority.

## DIAGNOSTIC_QUESTION_3
Given the URL `https://user:pass@www.example.com:8080/path/to/resource?query=value#fragment`, identify each of the six standard URL components and state the purpose of the port number `8080`.

## DIAGNOSTIC_ANSWER_3
Components: scheme=`https`, authority=`user:pass@www.example.com:8080` (userinfo=`user:pass`, host=`www.example.com`, port=`8080`), path=`/path/to/resource`, query=`query=value`, fragment=`fragment`. Port `8080` specifies the network port on the server to which the client should connect; it overrides the default port for HTTPS (443). A wrong answer that omits userinfo, treats the whole authority as host, or confuses query with fragment shows the student cannot parse the formal URL syntax (RFC 3986).

## DIAGNOSTIC_QUESTION_4
Compare a recursive DNS query and an iterative DNS query. Which type does a typical client (e.g., your laptop) send to its configured recursive resolver, and why?

## DIAGNOSTIC_ANSWER_4
In a recursive query, the resolver must return either the final answer or an error; it performs all intermediate lookups on behalf of the client. In an iterative query, the resolver returns the best answer it has (possibly a referral to another server), and the client must continue querying. A typical client sends a **recursive** query to its ISP/resolver because the client is a stub resolver with no capacity to chase referrals. If a student claims the client uses iterative queries, they confuse the client-resolver interaction with the resolver-to-authoritative-server interaction (which is iterative).

## DIAGNOSTIC_QUESTION_5
A website changes its hosting provider and thus its IP address every week. The administrator sets the TTL of the A record to 86400 seconds (1 day). Evaluate whether this TTL is appropriate. Justify your answer considering both propagation delay and cache efficiency.

## DIAGNOSTIC_ANSWER_5
The TTL of 86400 seconds is **too high** for weekly IP changes. With a 1-day TTL, recursive resolvers worldwide may cache the old IP for up to 24 hours after the change, causing visitors to reach the old server. A lower TTL (e.g., 300 seconds / 5 minutes) would ensure faster propagation of the new IP, at the cost of increased query load on authoritative servers. A student who says "high TTL is always better for performance" ignores the trade-off between cache efficiency and data freshness, a classic board exam trap.

## DIAGNOSTIC_QUESTION_6
Design a domain name structure for a multinational company "GlobalTech" that has offices in India (globaltech.in), USA (globaltech.us), and UK (globaltech.uk). Each office runs its own web server (www), mail server (mail), and internal database server (db). Show the fully qualified domain names (FQDNs) for all nine servers and specify which DNS record types you would create for each.

## DIAGNOSTIC_ANSWER_6
Example structure (using subdomains for offices):
- India web: `www.india.globaltech.in` → A record (IPv4) + AAAA record (IPv6)
- India mail: `mail.india.globaltech.in` → A/AAAA + MX record pointing to this host
- India db: `db.india.globaltech.in` → A/AAAA (internal only)
- USA web: `www.usa.globaltech.us` → A/AAAA
- USA mail: `mail.usa.globaltech.us` → A/AAAA + MX
- USA db: `db.usa.globaltech.us` → A/AAAA
- UK web: `www.uk.globaltech.uk` → A/AAAA
- UK mail: `mail.uk.globaltech.uk` → A/AAAA + MX
- UK db: `db.uk.globaltech.uk` → A/AAAA
Additionally, NS records at `globaltech.in`, `globaltech.us`, `globaltech.uk` delegate to each office's authoritative nameservers. A poor answer uses flat names like `www-india.globaltech.com` (not leveraging hierarchy) or omits MX records for mail, showing inability to map services to appropriate record types.

## COMMON_MISCONCEPTION
Students often believe that a DNS lookup always returns a single IPv4 address (A record). In reality, a domain can have multiple A records (load balancing), AAAA records (IPv6), CNAME aliases (www → example.com), MX records for email, and TXT records for verification. They also confuse the **domain name** (e.g., example.com) with the **URL** (e.g., https://example.com/path), writing "the DNS resolves the URL" instead of "DNS resolves the host part of the URL". This error costs marks in board questions asking "Which part of the URL is resolved by DNS?" and in competitive exams where they must identify the correct record type for a given service.

## WORKED_EXAMPLE_1
PROBLEM: Trace the complete DNS resolution process when a user in Mumbai types `https://www.iitb.ac.in` in a browser. Assume the browser and OS caches are empty, and the user's ISP recursive resolver has no cached data for this domain. List every query and response in order, naming the server type at each step.

STEPS:
- Step 1: Browser checks its internal cache → miss. OS resolver cache → miss. Browser sends a **recursive DNS query** for `www.iitb.ac.in` (A record) to the configured recursive resolver (e.g., ISP's resolver at 10.0.0.1).
- Step 2: Recursive resolver checks its cache → miss. It sends an **iterative query** to a **root nameserver** (e.g., a.root-servers.net) asking for `www.iitb.ac.in`.
- Step 3: Root nameserver does not know the answer but knows the authoritative servers for the `.in` TLD. It responds with a **referral** containing NS records and glue A/AAAA records for `.in` TLD nameservers (e.g., a.in.nic.in).
- Step 4: Recursive resolver sends an **iterative query** to a **.in TLD nameserver** (e.g., a.in.nic.in) for `www.iitb.ac.in`.
- Step 5: .in TLD nameserver does not have the final answer but knows the authoritative nameservers for `iitb.ac.in`. It responds with a **referral** containing NS records and glue records for `iitb.ac.in` authoritative nameservers (e.g., ns1.iitb.ac.in, ns2.iitb.ac.in).
- Step 6: Recursive resolver sends an **iterative query** to an **authoritative nameserver for iitb.ac.in** (e.g., ns1.iitb.ac.in) for `www.iitb.ac.in` A record.
- Step 7: Authoritative nameserver holds the zone data for `iitb.ac.in`. It finds the A record for `www` (e.g., 103.237.144.10) and returns the **authoritative answer** with the IP address and TTL.
- Step 8: Recursive resolver caches the A record (and any other records received) with the given TTL, then sends the final answer back to the client (browser).
- Step 9: Browser receives the IP address (103.237.144.10), establishes a TCP connection to port 443 (HTTPS), and sends the HTTP GET request.

REASONING: The process follows the DNS hierarchy from root to TLD to authoritative, with the recursive resolver doing the legwork on behalf of the stub resolver (client). Each referral moves one level down the tree. The use of iterative queries between resolver and authoritative servers reduces load on root/TLD servers, while the client uses a single recursive query.

ANSWER: The final resolved IP address is 103.237.144.10 (example). The sequence involved 1 recursive query (client→resolver) and 3 iterative queries (resolver→root, resolver→.in TLD, resolver→authoritative).

## WORKED_EXAMPLE_2
PROBLEM: Parse the following URL into its six standard components according to RFC 3986: `ftp://alice:secret@ftp.example.org:2121/pub/files/report.pdf?download=1#page5`. For each component, explain its role in locating the resource.

STEPS:
- Step 1: Identify the **scheme** — the substring before the first colon. Here `ftp` indicates the File Transfer Protocol.
- Step 2: Identify the **authority** — the substring between `//` and the next `/` (or end of string). Here `alice:secret@ftp.example.org:2121`.
- Step 3: Split authority into **userinfo** (`alice:secret`), **host** (`ftp.example.org`), and **port** (`2121`). Userinfo provides credentials; host is the domain name to be resolved via DNS; port overrides the default FTP port (21).
- Step 4: Identify the **path** — the substring after the authority up to `?` or `#` or end. Here `/pub/files/report.pdf` specifies the resource location on the server.
- Step 5: Identify the **query** — the substring after `?` up to `#` or end. Here `download=1` passes parameters to the server (e.g., force download).
- Step 6: Identify the **fragment** — the substring after `#`. Here `page5` is a client-side reference (e.g., a named anchor in a PDF) not sent to the server.

REASONING: The URL syntax is strictly hierarchical: scheme:[//authority]path[?query][#fragment]. Parsing proceeds left-to-right using delimiters `:`, `//`, `/`, `?`, `#`. The host component (`ftp.example.org`) is the only part that triggers a DNS lookup (to get A/AAAA records). The port tells the transport layer which server process to connect to.

ANSWER:
- scheme = `ftp`
- userinfo = `alice:secret`
- host = `ftp.example.org`
- port = `2121`
- path = `/pub/files/report.pdf`
- query = `download=1`
- fragment = `page5`

## WORKED_EXAMPLE_3
PROBLEM: A domain `shop.example.com` has the following DNS records in its zone file:
```
@       IN  A       203.0.113.10
www     IN  CNAME   shop.example.com.
mail    IN  A       203.0.113.20
@       IN  MX  10    mail.example.com.
@       IN  NS      ns1.example.com.
@       IN  NS      ns2.example.com.
```
A user visits `http://www.shop.example.com` and sends an email to `user@shop.example.com`. Determine the exact sequence of DNS queries and the final IP addresses used for the web server and the mail server. Assume all caches are empty.

STEPS:
- Step 1: **Web access** — Browser needs IP for `www.shop.example.com`. Resolver queries for A record of `www.shop.example.com`.
- Step 2: Authoritative nameserver (ns1/ns2) sees a **CNAME** record for `www` pointing to `shop.example.com.`. It returns the CNAME and also includes the A record for the target (`shop.example.com.`) in the additional section (or resolver follows up).
- Step 3: Resolver obtains **A record for `shop.example.com.`** → `203.0.113.10`. Browser connects to `203.0.113.10:80`.
- Step 4: **Email delivery** — Mail transfer agent (MTA) needs to deliver to `user@shop.example.com`. It queries for **MX records** of `shop.example.com`.
- Step 5: Authoritative nameserver returns **MX record**: priority 10, host `mail.example.com.`.
- Step 6: MTA now needs IP for `mail.example.com.`. It queries for **A record** of `mail.example.com.`.
- Step 7: Authoritative nameserver returns **A record**: `203.0.113.20`. MTA connects to `203.0.113.20:25` (SMTP).
- Step 8: Note that NS records (`ns1.example.com`, `ns2.example.com`) are used by resolvers to find the authoritative servers for the zone, but are not directly involved in the above two lookups once the resolver has found them.

REASONING: CNAME creates an alias; the resolver must canonicalize by following the CNAME to the true name (`shop.example.com`) and then fetch its A record. MX records point to a mail host name, which must itself be resolved to an IP address via A/AAAA lookup. This two-step process (MX → A) is standard for email routing.

ANSWER:
- Web server IP: `203.0.113.10` (via CNAME `www` → `shop.example.com` → A record)
- Mail server IP: `203.0.113.20` (via MX `shop.example.com` → `mail.example.com` → A record)

## COMPETENCY_QUESTION_1
QUESTION: DNS primarily uses UDP on port 53 for queries, but switches to TCP for responses larger than 512 bytes and for zone transfers (AXFR/IXFR). Explain why UDP is preferred for standard queries, and why TCP is necessary for large responses and zone transfers. Include in your answer the concepts of connection overhead, message truncation, and reliability.

COMPETENCY: Comparing and justifying protocol design choices

STEPS:
- Step 1: Recall that UDP is connectionless, low overhead, and fast — ideal for short request/response exchanges like a typical DNS query (≈ 100 bytes).
- Step 2: Note that UDP has no built-in fragmentation/reassembly at the application layer; if a response exceeds 512 bytes (traditional DNS limit), the server sets the TC (truncated) bit, and the client must retry over TCP.
- Step 3: Zone transfers involve transferring entire zone databases (thousands of records), requiring reliable, ordered, stream-oriented delivery — exactly what TCP provides.
- Step 4: Conclude that the dual-protocol design optimizes for the common case (small, fast UDP queries) while falling back to TCP for reliability and large data.

ANSWER: UDP avoids the three-way handshake and state maintenance, making it faster for the vast majority of DNS queries which fit in a single packet. TCP is used when the response is truncated (TC=1) because UDP cannot reliably deliver fragmented packets across firewalls, and for zone transfers because they require guaranteed, in-order delivery of large data streams. This design balances performance and correctness.

## COMPETENCY_QUESTION_2
QUESTION: You are the network administrator for a startup "EduTech" that has just registered `edutech.in`. The company needs:
- A public website at `www.edutech.in` (hosted on a cloud VM with IPv4 203.0.113.50 and IPv6 2001:db8::50).
- A blog at `blog.edutech.in` hosted on a separate platform that provides a hostname `blog-platform.edutech-hosting.com`.
- Email addresses `@edutech.in` handled by Google Workspace (MX records provided by Google: `aspmx.l.google.com`, `alt1.aspmx.l.google.com`, etc.).
- A wildcard subdomain `*.edutech.in` pointing to the same IP as `www` for future microservices.
- Delegation of `dev.edutech.in` to an external DNS provider `ns1.externaldns.com`, `ns2.externaldns.com`.

Write the complete set of DNS resource records (with proper syntax) for the `edutech.in` zone that satisfies all requirements. Explain the purpose of each record type used.

COMPETENCY: Translating real-world requirements to technical configuration

STEPS:
- Step 1: Create SOA record (mandatory for zone apex) and NS records for the zone's authoritative nameservers (assume `ns1.edutech.in`, `ns2.edutech.in` with A/AAAA glue records).
- Step 2: Add A and AAAA records for `@` (apex) and `www` pointing to the cloud VM IPs.
- Step 3: Add CNAME for `blog` pointing to `blog-platform.edutech-hosting.com.` (note trailing dot for FQDN).
- Step 4: Add MX records for `@` with priorities matching Google's specification (e.g., 1, 5, 5, 10, 10).
- Step 5: Add wildcard record `*.edutech.in. IN CNAME www.edutech.in.` (or A/AAAA directly) to cover all unspecified subdomains.
- Step 6: Add NS records for `dev.edutech.in` delegating to `ns1.externaldns.com.`, `ns2.externaldns.com.` (no glue needed if external).
- Step 7: Verify no conflicts (e.g., CNAME at apex is illegal — apex must have A/AAAA, not CNAME).

ANSWER:
```
$ORIGIN edutech.in.
$TTL 3600
@       IN  SOA  ns1.edutech.in. hostmaster.edutech.in. 2024010101 7200 3600 1209600 86400
@       IN  NS   ns1.edutech.in.
@       IN  NS   ns2.edutech.in.
ns1     IN  A    198.51.100.1
ns1     IN  AAAA 2001:db8::1
ns2     IN  A    198.51.100.2
ns2     IN  AAAA 2001:db8::2
@       IN  A    203.0.113.50
@       IN  AAAA 2001:db8::50
www     IN  A    203.0.113.50
www     IN  AAAA 2001:db8::50
blog    IN  CNAME blog-platform.edutech-hosting.com.
@       IN  MX 1  aspmx.l.google.com.
@       IN  MX 5  alt1.aspmx.l.google.com.
@       IN  MX 5  alt2.aspmx.l.google.com.
@       IN  MX 10 alt3.aspmx.l.google.com.
@       IN  MX 10 alt4.aspmx.l.google.com.
*       IN  CNAME www.edutech.in.
dev     IN  NS   ns1.externaldns.com.
dev     IN  NS   ns2.externaldns.com.
```
Purpose: SOA/NS define zone authority; A/AAAA map names to IPs; CNAME creates aliases (blog, wildcard); MX routes email; delegation NS hands off `dev` subdomain.
