## ELI5
Type www.cbse.gov.in — who knows the IP? The root knows .in, the TLD server knows gov.in, CBSE's authoritative server holds the A record. DNS is a hierarchical, distributed naming system translating human-readable domain names into machine-readable IP addresses through a multi-step resolution involving recursive resolvers, root servers, TLD servers, and authoritative name servers. It is a delegation chain — each level knows only the next, and caching cuts latency at every step.

## DEFINITION
DNS (Domain Name System) is a hierarchical, distributed naming system that translates human-readable domain names (e.g., www.example.com) into machine-readable IP addresses (e.g., 192.0.2.1) through a multi-step resolution process involving recursive resolvers, root servers, TLD servers, and authoritative name servers.

## WALKTHROUGH
Imagine you type "www.cbse.gov.in" in your browser — how does your computer find the IP address of the CBSE server? You already know IP addresses from c12_ip_cbse_03_006 and the client-server model from c12_ip_cbse_03_008. Start by asking: "Who knows the IP for .in domains?" This leads to the root server. Then: "Who knows cbse.gov.in?" This leads to the .in TLD server. Finally: "What is the A record for www.cbse.gov.in?" This leads to CBSE's authoritative server. The key insight is that DNS is a delegation chain — each level only knows the next level, not the final answer.

Takeaway: mastery means the chain walked server by server — and the root's ignorance respected. Exam moves: tracing questions follow the full resolution path naming each server type; record questions identify the A record exchange; caching questions explain latency and load reductions at each level. Method: run the lookup — resolver, root, TLD, authoritative — then ask the same query twice and watch the cache answer. Drill: four server types, one record, one cache story. Students miss it because the root feels omniscient — the lesson flags exactly that. The cache is the payoff: run it twice, and the second answer never leaves your machine.

## DIAGNOSTIC_QUESTION_1
What is the primary function of a recursive resolver in the DNS resolution process?

## DIAGNOSTIC_ANSWER_1
A recursive resolver accepts a DNS query from a client (stub resolver) and performs the entire iterative lookup on the client's behalf — querying root, TLD, and authoritative servers sequentially — until it obtains the final IP address or an error, then returns the answer to the client. A wrong answer (e.g., "it only queries the root server" or "it caches only") reveals the student confuses recursive resolvers with root/TLD servers or misunderstands that the resolver does the full work so the client doesn't have to.

## DIAGNOSTIC_QUESTION_2
Explain the difference between an A record and a CNAME record in DNS, and give one scenario where you would use each.

## DIAGNOSTIC_ANSWER_2
An A record maps a domain name directly to an IPv4 address (e.g., www.example.com → 192.0.2.1). A CNAME record maps a domain name to another domain name (alias), which must then be resolved to an IP (e.g., blog.example.com → www.example.com). Use A for the canonical name pointing to an IP; use CNAME for subdomains/services that should always follow the canonical name's IP (e.g., when migrating servers, update only the A record). A wrong answer (e.g., "CNAME points to IP" or "both do the same") reveals confusion between direct mapping and aliasing — a critical distinction for zone management.

## DIAGNOSTIC_QUESTION_3
A user types "mail.google.com" in their browser. The local DNS cache is empty. Trace the complete DNS resolution path, naming each server type contacted and the query/response at each step.

## DIAGNOSTIC_ANSWER_3
Step 1: Stub resolver → Recursive resolver: query for mail.google.com A record.
Step 2: Recursive resolver → Root server: query for mail.google.com A record. Root responds with referral to .com TLD servers (NS records for .com).
Step 3: Recursive resolver → .com TLD server: query for mail.google.com A record. TLD responds with referral to google.com authoritative name servers (NS records for google.com).
Step 4: Recursive resolver → google.com authoritative server: query for mail.google.com A record. Authoritative responds with A record (IP address) or CNAME (e.g., mail.google.com → googlemail.l.google.com) followed by A record for the target.
Step 5: Recursive resolver caches the result and returns IP to stub resolver.
A wrong answer (e.g., skipping root/TLD, or saying root returns IP) reveals the student doesn't grasp the delegation hierarchy — the most common board exam error.

## DIAGNOSTIC_QUESTION_4
Compare recursive and iterative DNS queries. Why does the recursive resolver use iterative queries to root/TLD/authoritative servers, while the client uses a recursive query to the resolver?

## DIAGNOSTIC_ANSWER_4
In a recursive query, the queried server must return the final answer or an error — it cannot refer the client elsewhere. In an iterative query, the server returns the best answer it has (often a referral to another server). The client (stub resolver) uses a recursive query to the recursive resolver because it lacks the logic to follow referrals. The recursive resolver uses iterative queries to root/TLD/authoritative servers because those servers are configured to only give referrals (iterative responses) — they don't perform full lookups for others. A wrong answer (e.g., "recursive resolver uses recursive queries to root") reveals misunderstanding of server roles and query types — a frequent JEE/NEET trap.

## DIAGNOSTIC_QUESTION_5
Evaluate this statement: "DNS caching only happens at the recursive resolver; root and TLD servers never cache." Defend your answer with technical reasoning.

## DIAGNOSTIC_ANSWER_5
The statement is FALSE. Caching occurs at EVERY level: recursive resolver caches all responses (including referrals from root/TLD); root and TLD servers cache negative responses and referrals they receive during their own operations (though they primarily serve cached zone data); even the client OS and browser maintain DNS caches. Caching at root/TLD is critical — without it, every .com query would hit the root again, creating massive load. A wrong answer (agreeing with the statement) reveals the student thinks caching is exclusive to recursive resolvers, missing the distributed caching architecture that makes DNS scalable.

## DIAGNOSTIC_QUESTION_6
Design a DNS zone file snippet for "example.com" that includes: an A record for www pointing to 192.0.2.10, a CNAME for blog pointing to www, an MX record for mail handled by mail.example.com (priority 10), and an NS record delegating "sub.example.com" to ns1.sub.example.com (IP 192.0.2.20). Write the zone file entries in standard BIND format.

## COMMON_MISCONCEPTION
Students believe the root server returns the IP address of the final domain (e.g., "root knows www.google.com's IP"). In reality, root servers only know the IP addresses of TLD servers (.com, .in, .org). They return a referral (NS records) for the TLD. This error stems from thinking DNS is a flat lookup table rather than a delegation hierarchy. In board exams, students write "root server gives IP of google.com" and lose 2-3 marks. In JEE, this appears as a trap in "which server returns the authoritative answer?" — the root never does.

## WORKED_EXAMPLE_1
PROBLEM: A student types "www.niit.edu.in" in a browser. The local DNS cache and OS cache are empty. The recursive resolver's cache has the .in TLD server IP but not the niit.edu.in authoritative server. Trace the DNS messages (query/response) exchanged, naming the record types in each response.

STEPS:
- Step 1: Identify the starting point — stub resolver sends recursive query for www.niit.edu.in A record to recursive resolver (configured via DHCP).
- Step 2: Recursive resolver checks cache — finds .in TLD server IP (NS record for .in with glue A record), but no niit.edu.in NS records. It sends iterative query to .in TLD server for www.niit.edu.in A record.
- Step 3: .in TLD server responds with referral: NS records for edu.in zone (authoritative for edu.in) and glue A records for those NS hostnames.
- Step 4: Recursive resolver sends iterative query to edu.in authoritative server for www.niit.edu.in A record.
- Step 5: edu.in authoritative server responds with referral: NS records for niit.edu.in zone and glue A records.
- Step 6: Recursive resolver sends iterative query to niit.edu.in authoritative server for www.niit.edu.in A record.
- Step 7: niit.edu.in authoritative server responds with authoritative answer: A record for www.niit.edu.in (e.g., 203.0.113.45).
- Step 8: Recursive resolver caches all received records (TTL-based) and returns A record to stub resolver.

REASONING: Each delegation step moves one level down the DNS hierarchy. The recursive resolver follows referrals iteratively because root/TLD/authoritative servers only give referrals (iterative responses). Record types: query is always A (or AAAA); responses contain NS (referral) or A (answer) with glue records to avoid circular dependency.

ANSWER: Resolution path: Stub → Recursive → .in TLD → edu.in auth → niit.edu.in auth. Responses: .in TLD gives NS+glue for edu.in; edu.in auth gives NS+glue for niit.edu.in; niit.edu.in auth gives A record for www.niit.edu.in.

## WORKED_EXAMPLE_2
PROBLEM: An organization "example.org" wants to host its website at www.example.org (IP 198.51.100.10), email at mail.example.org (handled by mail server mx1.example.org at 198.51.100.20), and a blog at blog.example.org (alias to www). They also delegate subdomain "dev.example.org" to an external provider with nameserver ns1.devprovider.net (IP 203.0.113.50). Write the complete zone file for example.org with appropriate TTL, SOA, and all records.

STEPS:
- Step 1: Set $ORIGIN and $TTL at top for zone-wide defaults.
- Step 2: Write SOA record: primary NS (ns1.example.org), responsible person (hostmaster.example.org), serial (YYYYMMDDNN), refresh/retry/expire/minimum TTL values per RFC 1035.
- Step 3: Add NS records for example.org zone (ns1.example.org, ns2.example.org) with glue A records.
- Step 4: Add A record for www.example.org → 198.51.100.10.
- Step 5: Add CNAME record for blog.example.org → www.example.org.
- Step 6: Add A record for mx1.example.org → 198.51.100.20.
- Step 7: Add MX record for @ (apex) → mx1.example.org with priority 10.
- Step 8: Add delegation for dev.example.org: NS record for dev → ns1.devprovider.net, and glue A record for ns1.devprovider.net → 203.0.113.50 (required because NS is in external domain).

REASONING: Zone file must be self-contained for delegation — glue records prevent circular lookups. MX points to a hostname (not IP), so that hostname must have an A record. CNAME cannot coexist with other records for same name (so blog cannot have its own A/TXT). SOA serial must increment on each change for zone transfer.

ANSWER:
```
$ORIGIN example.org.
$TTL 3600
@       IN  SOA ns1.example.org. hostmaster.example.org. 2024121901 7200 3600 1209600 86400
@       IN  NS  ns1.example.org.
@       IN  NS  ns2.example.org.
ns1     IN  A   198.51.100.1
ns2     IN  A   198.51.100.2
www     IN  A   198.51.100.10
blog    IN  CNAME   www
mx1     IN  A   198.51.100.20
@       IN  MX  10  mx1.example.org.
dev     IN  NS  ns1.devprovider.net.
ns1.devprovider.net. IN  A   203.0.113.50
```

## WORKED_EXAMPLE_3
PROBLEM: A recursive resolver receives a query for "api.service.company.co.uk". Its cache contains: (1) root hints, (2) .uk TLD server IPs, (3) co.uk authoritative server IPs, (4) company.co.uk NS records (ns1.company.co.uk, ns2.company.co.uk) but NO glue A records for those NS hostnames. The resolver has NO cached data for service.company.co.uk or api.service.company.co.uk. Trace the exact queries the resolver sends and the responses it expects, including the additional step needed due to missing glue.

STEPS:
- Step 1: Resolver has .uk TLD IPs — sends iterative query to .uk TLD for api.service.company.co.uk A.
- Step 2: .uk TLD responds with referral: NS records for co.uk zone + glue A records for co.uk NS hostnames.
- Step 3: Resolver has co.uk auth IPs (cached) — sends iterative query to co.uk auth for api.service.company.co.uk A.
- Step 4: co.uk auth responds with referral: NS records for company.co.uk (ns1.company.co.uk, ns2.company.co.uk) but NO glue A records (missing).
- Step 5: Resolver cannot contact company.co.uk auth without their IPs — must resolve ns1.company.co.uk first. Sends recursive query to itself (or new iterative chain) for ns1.company.co.uk A.
- Step 6: This sub-resolution follows same path: .uk TLD → co.uk auth → company.co.uk auth (which now gives A for ns1.company.co.uk).
- Step 7: With ns1 IP, resolver sends iterative query to ns1.company.co.uk for api.service.company.co.uk A.
- Step 8: company.co.uk auth responds with referral: NS records for service.company.co.uk (if delegated) or authoritative answer if not delegated.
- Step 9: If service.company.co.uk is delegated, repeat for its auth servers; else, company.co.uk auth gives A for api.service.company.co.uk (or CNAME).
- Step 10: Resolver caches all, returns final answer to client.

REASONING: Missing glue records force an additional resolution sub-task (glue fetch). This is a real-world scenario — zone administrators must provide glue for child zone NS hostnames that fall within the child zone (in-bailiwick). The resolver handles this transparently but it adds latency. Board exams test this via "what happens if glue is missing?" — answer: resolver must resolve the NS hostname first.

ANSWER: Extra resolution for ns1.company.co.uk A record inserted between Step 4 and Step 7. Total queries: .uk TLD → co.uk auth → (ns1.company.co.uk resolution: .uk TLD → co.uk auth → company.co.uk auth) → company.co.uk auth → (possibly service.company.co.uk auth).

## COMPETENCY_QUESTION_1
QUESTION: A school network administrator configures the local recursive resolver to forward all queries to Google's public DNS (8.8.8.8) instead of performing iterative resolution. A student claims this "bypasses DNS hierarchy." Evaluate this claim. Explain what actually changes in the resolution path, and identify one advantage and one disadvantage of this forwarding setup.

COMPETENCY: Translating real-world situations to technical explanations and comparing design trade-offs

STEPS:
- Step 1: Understand the claim — "bypasses hierarchy" suggests root/TLD/authoritative servers are skipped.
- Step 2: Identify the actual change — the school's resolver becomes a stub resolver; Google's resolver performs the full iterative hierarchy walk.
- Step 3: Explain — hierarchy is still fully traversed, just by Google's servers instead of school's. The query path becomes: Student → School Resolver (forward) → Google Resolver (iterative: root → TLD → auth) → Google Resolver → School Resolver → Student.
- Step 4: Advantage — reduced latency for popular domains (Google's cache is huge/hot), offloads school's resolver, centralizes cache.
- Step 5: Disadvantage — single point of failure (if 8.8.8.8 down, all resolution fails), privacy concern (Google sees all queries), no local policy control (e.g., blocking malicious domains via RPZ).

ANSWER: The claim is FALSE. DNS hierarchy (root → TLD → authoritative) is still fully traversed — only the entity performing the iterative walk changes from the school's resolver to Google's resolver. Advantage: better cache hit rate, lower latency for common domains. Disadvantage: dependency on external provider, privacy exposure, loss of local filtering control.

## COMPETENCY_QUESTION_2
QUESTION: During a CTF competition, you capture a DNS response packet with the following flags: QR=1, Opcode=0, AA=1, TC=0, RD=1, RA=1, Z=0, RCODE=0. The question section contains "flag.ctf.example.com" type A. The answer section contains "flag.ctf.example.com. 300 IN A 10.10.10.10". The authority section contains "ctf.example.com. 3600 IN NS ns1.ctf.example.com." and "ctf.example.com. 3600 IN NS ns2.ctf.example.com." The additional section contains glue records for ns1 and ns2. Analyze this response: (a) Who sent this response? (b) Is it authoritative? (c) What does the presence of NS records in authority section indicate? (d) Why are glue records in additional section?

COMPETENCY: Error identification and correction / Analyzing protocol artifacts

STEPS:
- Step 1: Analyze flags — QR=1 (response), Opcode=0 (standard query), AA=1 (authoritative answer), RA=1 (recursion available).
- Step 2: (a) AA=1 means the responding server is authoritative for the zone (ctf.example.com). So: authoritative name server for ctf.example.com.
- Step 3: (b) YES, AA=1 confirms authoritative answer.
- Step 4: (c) NS records in authority section indicate delegation — the zone ctf.example.com is delegated to ns1/ns2.ctf.example.com. Since the query was for flag.ctf.example.com (a subdomain), and the answer came from ctf.example.com auth, this suggests flag.ctf.example.com is NOT further delegated (otherwise we'd get referral).
- Step 5: (d) Glue records (A for ns1/ns2) in additional section prevent circular dependency: to resolve ns1.ctf.example.com, you'd need to query ctf.example.com auth — but you're already talking to it! Glue provides IPs directly.

ANSWER: (a) Authoritative name server for ctf.example.com. (b) Yes, AA=1. (c) The zone ctf.example.com is served by ns1/ns2.ctf.example.com; flag.ctf.example.com is within this zone (not delegated further). (d) Glue records provide IP addresses for the NS hostnames to avoid circular resolution — without them, resolving ns1.ctf.example.com would require querying the same server we're trying to reach.

DIFFICULTY: hard
