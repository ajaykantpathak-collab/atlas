## ELI5
The school's About Us page shows every visitor the same mission statement; your timetable page is rebuilt for your roll number alone. A static web page delivers identical pre-written HTML, CSS, and JavaScript without server-side processing — the server just reads a file. A dynamic web page executes server-side code that may query databases and process input before sending HTML. Ask: does this page change with who is asking or when? Static is file retrieval; dynamic is execution.

## DEFINITION
A static web page delivers identical pre-written HTML/CSS/JS content to every user without server-side processing, while a dynamic web page generates customised content per request by executing server-side code (PHP, Python, JavaScript, etc.) that may query databases, process user input, or compute real-time data before sending the HTML response.

## MASTERY_CRITERIA

## SCOPE_BOUNDARY

## WALKTHROUGH
Imagine you visit your school's website: the "About Us" page shows the same history and mission statement to every visitor — that's a static page. Now you log into the student portal to see your personal timetable and marks — that page is built dynamically for *you* using your roll number to query a database. Start by asking: "Does this page change based on *who* is asking or *when* they ask?" If yes → dynamic. If no → static. Then trace the HTTP request: for static, the server just reads a file from disk and sends it; for dynamic, the server runs a program, talks to a database, builds HTML on the fly, then sends it. The key insight: **static = file retrieval; dynamic = program execution + file retrieval**.

Takeaway: mastery means the test applied first — does the page change with who asks or when — then the two server behaviours separated. Exam moves: distinction questions classify pages from behaviour or source code; flow questions trace static file retrieval against dynamic program execution plus database access; reasoning questions place the timetable and the About Us page. Method: open both pages, ask the change-question, then picture the server reading a file versus running a program. Drill: two pages, two flows, one question. Students miss it because both arrive as HTML — the planted difference lives before the send.

## DIAGNOSTIC_QUESTION_1
A student claims: "Any web page that has animations or moving images must be a dynamic web page." Is this statement correct? Explain why or why not in 2-3 sentences.

## DIAGNOSTIC_ANSWER_1
The statement is **incorrect**. A static web page can contain animations, videos, and interactive elements using CSS animations, JavaScript, or embedded media — all delivered as pre-written files. "Dynamic" refers to *server-side content generation per request*, not client-side visual effects. A page with a CSS loading spinner served from a .html file is static; a page that shows "Welcome, [YourName]" after querying a user table is dynamic.

## DIAGNOSTIC_QUESTION_2
You are given two URLs: `https://example.com/about.html` and `https://example.com/profile.php?id=101`. Without visiting them, how can you infer which is likely static and which is dynamic? What specific clues in the URL structure suggest this?

## DIAGNOSTIC_ANSWER_2
`about.html` suggests a **static** page — the `.html` extension typically indicates a pre-existing file served directly. `profile.php?id=101` suggests a **dynamic** page — the `.php` extension indicates a server-side script, and the query parameter `id=101` implies the page content depends on a variable input (user ID) that will be used to fetch specific data from a database. Wrong answers reveal confusion between file extensions and actual server behaviour; some dynamic pages use URL rewriting to hide extensions.

## DIAGNOSTIC_QUESTION_3
A web developer creates a page `weather.html` that shows the current temperature for Delhi. The page uses JavaScript's `fetch()` to call a public weather API and updates the DOM with the response. Is this a static or dynamic web page? Justify your answer by describing the request-response flow.

## DIAGNOSTIC_ANSWER_3
This is a **static web page** from the server's perspective. The server delivers the identical `weather.html` file (containing HTML, CSS, and JavaScript code) to every user. The *dynamic behaviour* (fetching live weather data) happens **client-side** in the browser via JavaScript calling an external API. The web server does not execute any code or query a database to generate the page. Students often confuse client-side dynamism with server-side dynamism — this distinction is critical for board exams.

## DIAGNOSTIC_QUESTION_4
Compare the server-side processing steps when a browser requests (a) a static `.html` page and (b) a dynamic `.php` page that displays a user's order history from a MySQL database. List the steps in order for each case and highlight the *additional* steps in the dynamic case.

## DIAGNOSTIC_ANSWER_4
**Static (.html):**
1. Browser sends HTTP GET request for `/orders.html`
2. Web server (e.g., Apache/Nginx) locates `orders.html` in filesystem
3. Server reads file content
4. Server sends HTTP 200 response with file content as body

**Dynamic (.php with MySQL):**
1. Browser sends HTTP GET request for `/orders.php?user=101`
2. Web server passes request to PHP interpreter (via FastCGI/module)
3. PHP script executes: connects to MySQL → runs `SELECT * FROM orders WHERE user_id=101`
4. PHP script builds HTML string using fetched data
5. PHP returns generated HTML to web server
6. Server sends HTTP 200 response with generated HTML

**Additional steps in dynamic case:** 3, 4, 5 (database connection, query execution, HTML generation). Wrong answers often omit the PHP interpreter step or think the web server directly queries the database.

## DIAGNOSTIC_QUESTION_5
A startup wants to build a website with these pages: (i) Home page with company info, (ii) Product catalogue with 500 items, (iii) User dashboard showing personal orders, (iv) Contact form that emails the company. For each page, recommend static or dynamic and justify. Which *one* page could be implemented either way, and what would be the trade-off?

## DIAGNOSTIC_ANSWER_5
(i) **Static** — same content for all, rarely changes.
(ii) **Dynamic** — 500 items imply a database; easier to manage/update via CMS.
(iii) **Dynamic** — personalised per user, requires authentication + database query.
(iv) **Dynamic** — form processing needs server-side code (email sending, validation).

**Page (i) Home page** could be either. **Static trade-off:** faster load, cheaper hosting, but every content change requires code edit + redeploy. **Dynamic trade-off:** editable via CMS/admin panel, but slower (DB query + template rendering) and more complex infrastructure. Wrong answers often say "all dynamic" or "all static" without justifying based on *content variability* and *data source*.

## DIAGNOSTIC_QUESTION_6
Design a minimal example showing how the *same* visual page (a greeting "Hello, [Name]!") can be implemented as (a) a static page with client-side JavaScript and (b) a dynamic page with server-side Python (Flask). Write the key code snippets for both and explain where the name "Aarav" comes from in each case.

## DIAGNOSTIC_ANSWER_6
**(a) Static + Client-side JS:**
```html
<!-- greeting.html (served identically to all) -->
<h1 id="greeting"></h1>
<script>
  const name = new URLSearchParams(window.location.search).get('name') || 'Guest';
  document.getElementById('greeting').textContent = `Hello, ${name}!`;
</script>
```
Name "Aarav" comes from **URL query parameter** `?name=Aarav` read by browser JS.

**(b) Dynamic (Flask):**
```python
# app.py
@app.route('/greet')
def greet():
    name = request.args.get('name', 'Guest')  # from query string
    return f'<h1>Hello, {name}!</h1>'  # HTML generated on server
```
Name "Aarav" comes from **server-side request parsing** before HTML is sent.

**Key difference:** In (a), the server sends *code* that the browser executes; in (b), the server sends *already-computed HTML*. Poor answers conflate the two or fail to identify the execution environment.

## COMMON_MISCONCEPTION
**Misconception:** "Dynamic web pages are those that look interactive or have moving parts; static pages are plain and boring."
**Why it's wrong:** Students equate *visual dynamism* (animations, carousels, AJAX updates) with *server-side dynamism*. A page with a JavaScript-powered image slider served as a `.html` file is **static** — the server does zero processing per request. Conversely, a plain-looking page showing "Your balance: ₹12,345" generated by querying a banking database is **dynamic** despite having zero animations.
**Concrete error:** In board exams, students classify a weather dashboard using client-side `fetch()` as "dynamic web page" and lose marks. NCERT defines dynamic pages by **server-side content generation** (Section 5.8.1: "server may perform some additional processes like getting information from the database... before sending the requested web page").

## ON_FAILURE
If a student confuses client-side vs server-side dynamism:
1. **Revisit** `c12_ip_cbse_05_004` (Web browsers and web servers) — focus on the HTTP request-response cycle: who sends what, who executes code.
2. **Trace** two requests on paper: (a) `GET /page.html` → server reads file → sends bytes; (b) `GET /page.php` → server invokes PHP → PHP runs SQL → builds HTML → sends bytes.
3. **Re-diagnostic:** Give them a `.html` file containing `<script>fetch('/api/data').then(...)</script>` and ask: "Does the web server execute this JavaScript?" Answer: No, the browser does. The server only transmits the file. This clinches the distinction.

## WORKED_EXAMPLE_1
PROBLEM: A school website has three pages: (1) `index.html` — welcome message and school logo, (2) `timetable.php?class=12A` — shows Class 12A's weekly schedule from a MySQL database, (3) `contact.html` — a form that submits to `submit.php`. Classify each as static or dynamic. For the dynamic ones, write the exact sequence of server-side steps from HTTP request to HTTP response.

STEPS:
- Step 1: Identify the file extension and whether content varies per user/request. `index.html` and `contact.html` have `.html` extension and show same content to everyone → static. `timetable.php` has `.php` extension and takes a query parameter `class=12A` → dynamic.
- Step 2: For `timetable.php`, trace server-side flow: (a) Web server (Apache) receives `GET /timetable.php?class=12A`, (b) Passes to PHP interpreter via FastCGI, (c) PHP script runs: `$class = $_GET['class']; $sql = "SELECT * FROM timetable WHERE class='$class'"; $result = mysqli_query($conn, $sql);`, (d) PHP loops through `$result` and builds HTML table rows, (e) PHP outputs complete HTML, (f) Web server sends HTTP 200 with generated HTML.
- Step 3: For `contact.html` → static file served directly. But `submit.php` (form handler) is dynamic: receives POST data, validates, inserts into `enquiries` table, sends confirmation email, returns success page.
- Step 4: Verify classification against NCERT definition: static = "content always remains static... server just locates the page... and sends it"; dynamic = "server may perform some additional processes like getting information from the database... before sending".
- Step 5: Conclude: `index.html` (static), `contact.html` (static), `timetable.php` (dynamic), `submit.php` (dynamic).

REASONING: Classification hinges on whether the server executes code per request. File extension (.html vs .php/.py/.jsp) is a strong heuristic but not absolute (URL rewriting can hide extensions). The defining factor: does the server run a program that computes the response?

ANSWER: index.html — static; contact.html — static; timetable.php — dynamic (PHP + MySQL); submit.php — dynamic (PHP + MySQL + email).

## WORKED_EXAMPLE_2
PROBLEM: A developer wants to show the current date and time on a web page. Show two implementations: (A) Pure static HTML + client-side JavaScript, (B) Server-side Python (Flask). For each, write the code and explain what the *browser receives* in the HTTP response body.

STEPS:
- Step 1: Implementation A (static + client-side JS): Create `time.html` with `<span id="clock"></span><script>setInterval(() => { document.getElementById('clock').textContent = new Date().toLocaleString(); }, 1000);</script>`. The server sends this exact file to every user — the response body contains the HTML+JS code, not the actual time.
- Step 2: Implementation B (dynamic Flask): `app.py` with `@app.route('/time') def show_time(): return f'<h1>Current time: {datetime.now().strftime("%d-%m-%Y %H:%M:%S")}</h1>'`. The server executes Python, computes the time string, interpolates into HTML, and sends the *resulting HTML* (e.g., `<h1>Current time: 15-10-2024 14:30:05</h1>`) — no JavaScript in response.
- Step 3: Compare response bodies: (A) contains `<script>...new Date()...</script>` — time computed by browser every second. (B) contains static timestamp — time computed once on server at request moment.
- Step 4: Identify trade-offs: (A) reduces server load, works offline after load, but shows *client's* clock (may be wrong). (B) shows *server's* accurate time, but increases server load (one execution per request) and cannot update without refresh.
- Step 5: Map to NCERT: (A) is static — "server just locates the page... no additional processing". (B) is dynamic — "server may perform some additional processes like updating date and time... before sending".

REASONING: The same visual feature (showing time) can be static or dynamic depending on *where* the computation happens. This distinction is examinable: "A web page shows current time using JavaScript. Is it static or dynamic?" Answer: Static, because server does no processing.

ANSWER: 
(A) Static — browser receives HTML+JS code; time computed client-side. 
(B) Dynamic — browser receives pre-computed HTML with timestamp; time computed server-side.

## WORKED_EXAMPLE_3
PROBLEM: An e-commerce site has a product page `product.php?id=101` that shows details of product ID 101 from a database. The page also includes a "Related Products" section showing 4 random products from the same category. The site gets 10,000 visits/day. The developer considers two architectures: (X) Fully dynamic — every request runs 2 SQL queries (product + related), builds HTML in PHP. (Y) Static site generator — pre-render all 5,000 product pages as `.html` files nightly via a script; serve static files. Compare X and Y on: (a) server CPU load, (b) data freshness, (c) storage, (d) ability to show "Only 2 left in stock!" real-time. Which is better for this scale? Justify.

STEPS:
- Step 1: Define architecture X (dynamic): Each visit → PHP process starts → 2 DB queries → HTML generation → response. 10,000 visits/day = ~7 req/min average, but peaks higher. CPU: moderate-high (process spawn + DB + templating). Data freshness: real-time (stock, price always current). Storage: minimal (only DB + templates). Real-time stock: YES.
- Step 2: Define architecture Y (static generation): Nightly cron runs → loops 5,000 products → 2 queries each → writes 5,000 `.html` files to disk. Daytime: Nginx serves static files (zero PHP, zero DB). CPU: near-zero at runtime (static file serve is microseconds). Data freshness: stale until next rebuild (stock/price updates not reflected). Storage: 5,000 HTML files (~50-100 MB). Real-time stock: NO (shows yesterday's stock).
- Step 3: Compare for 10k visits/day: X handles real-time needs but needs PHP-FPM workers + DB connections; Y is blazing fast/cheap to host but cannot show live stock. Hybrid approach common: static HTML for product details + client-side JS fetch for stock/price (AJAX).
- Step 4: Board exam angle: NCERT says dynamic pages "take more time to load than static web pages" and "content changes frequently". This example shows the *reason*: server-side computation per request.
- Step 5: Recommendation: For 10k visits with real-time stock requirement → Architecture X (or hybrid). If stock updates only daily → Architecture Y (cheaper, faster).

REASONING: This problem combines static/dynamic distinction with scalability, caching, and data freshness — exactly the kind of multi-concept reasoning CBSE competency questions and CUET/JEE-style questions test. It requires understanding that "dynamic" implies per-request computation cost, while "static" implies pre-computation + storage cost.

ANSWER: Architecture X (dynamic) better for real-time stock; Architecture Y (static) better for performance/cost if data changes infrequently. Hybrid (static HTML + AJAX for stock) is industry best practice.

## COMPETENCY_QUESTION_2
QUESTION: A news website publishes 200 articles/day. The homepage shows the 10 latest articles. The site currently uses a dynamic PHP page `index.php` that runs `SELECT * FROM articles ORDER BY published_at DESC LIMIT 10` on every visit. The CTO proposes switching to a static site generator that rebuilds `index.html` every 5 minutes via a cron job. Analyse both approaches for: (a) database load, (b) content freshness (max delay for new article to appear), (c) traffic spike handling (e.g., breaking news → 100x traffic). Recommend the better approach for this specific use case with justification.

COMPETENCY: Comparing and justifying architectural trade-offs using systems thinking

STEPS:
- Step 1: Current dynamic approach: Every visit → 1 DB query. 1000 visits/min → 1000 queries/min. DB load = high. Freshness = real-time (instant). Traffic spike: each visitor adds DB + PHP load → risk of overload.
- Step 2: Proposed static approach: Cron every 5 min → 1 DB query per rebuild. Daytime: zero DB queries (static file serve). DB load = negligible (12 queries/hour). Freshness = max 5 min delay. Traffic spike: static file serve handles 100x easily (Nginx serves 10k+ req/sec on modest hardware).
- Step 3: Evaluate for news site: Breaking news needs freshness, but 5-min delay is acceptable. Traffic spikes are the real danger — dynamic approach crashes under load; static survives.
- Step 4: Recommend static generation with 5-min rebuild. Cite NCERT: "Dynamic web pages... take more time to load than static web pages" — under load, this becomes unavailability.
- Step 5: Bonus: Mention incremental static regeneration (Next.js `revalidate`) as modern hybrid — but not in NCERT scope.

ANSWER: Static generation (5-min rebuild) is better. DB load drops from 1000 qpm to 0.2 qpm. Freshness: ≤5 min delay (acceptable for news). Traffic spikes: static handles 100x easily; dynamic crashes. NCERT confirms dynamic pages are slower and more resource-intensive.

DIFFICULTY: hard
